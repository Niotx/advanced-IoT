## ۱۱. ارتباطات فراتر از Wi-Fi — بخش دهم دوره (Slides 43–48)

**مسئله:** تا اینجا ESP32 و Raspberry Pi در یک شبکه محلی دارای Wi-Fi کار می‌کردند. حالا فرض کنید یک سنسور دما و رطوبت در مزرعه‌ای دور از Access Point نصب شده و فقط هر چند دقیقه یک پیام کوچک ارسال می‌کند. چه فناوری ارتباطی با محدودیت پوشش، انرژی، هزینه و زمان پاسخ‌گویی سازگارتر است؟

> **وضعیت این بخش:** محتوای اسلایدهای ۴۳ تا ۴۸ **مفهومی و معماری** است. در این دوره برای Cellular یا LoRaWAN کد اجرایی، آزمایش برد، اندازه‌گیری برد/توان یا راه‌اندازی Gateway انجام نداده‌ایم. اعداد عملکردی بدون تجهیزات و تست میدانی گزارش نمی‌شوند؛ **پوشه نمونه اجرایی جداگانه‌ای هم برای این بخش وجود ندارد**.

### ۱. مسئله انتخاب ارتباط (Slide 43)

قبل از انتخاب فناوری، نیازمندی‌ها را مشخص کنید: موقعیت نصب و پوشش واقعی، منبع تغذیه (باتری یا برق ثابت)، اندازه و فاصله زمانی پیام‌ها، حداکثر تأخیر قابل قبول برای Downlink، تعداد دستگاه‌ها، زیرساخت موجود، هزینه اولیه و هزینه نگهداری. **LPWAN** خانواده‌ای از راهکارهای شبکه گسترده با تمرکز بر دستگاه‌های کم‌مصرف و داده کم‌حجم است؛ هر ارتباط سلولار 4G الزاماً LPWAN نیست.

### ۲. Cellular IoT: 2G / 4G (Slide 44)

در راهکار سلولار، ESP32 معمولاً با **UART** و **AT Commands** به مودم سازگار متصل می‌شود. مودم با **SIM، تنظیمات APN و آنتن مناسب** از شبکه اپراتور برای انتقال داده استفاده می‌کند؛ ESP32 به‌تنهایی مودم سلولار ندارد.

```text
DHT22 → ESP32 → UART → Cellular Modem + SIM + Antenna
                                     ↓
                            Mobile Operator Network
                                     ↓
                              Internet / Backend
```

چند دستور متداول برای **آشنایی با نقش AT Commands** (نه یک راهنمای اجرایی وابسته به مودم مشخص):

| دستور | کاربرد متداول |
|---|---|
| `AT` | آزمایش پاسخ‌دهی رابط مودم |
| `AT+CPIN?` | بررسی آماده‌بودن SIM |
| `AT+CSQ` | دریافت نشانگر کلی قدرت سیگنال؛ به‌تنهایی معیار کامل کیفیت LTE نیست |
| `AT+CREG?` / `AT+CEREG?` | بررسی وضعیت ثبت‌نام در شبکه‌های مربوط، بسته به نوع مودم و شبکه |

**قبل از خرید:** فعال‌بودن 2G/4G در محل و نزد اپراتور، باندهای فرکانسی مودم، پشتیبانی SIM/APN، سازگاری سطح ولتاژ UART، **جریان لحظه‌ای منبع تغذیه**، آنتن و هزینه اشتراک را بررسی کنید. 2G ممکن است در بعضی کشورها یا شبکه‌ها خاموش شده یا در حال خروج از سرویس باشد. گزینه‌های اختصاصی IoT سلولار مثل LTE-M و NB-IoT نیز فقط در صورت پشتیبانی واقعی اپراتور قابل بررسی‌اند.

### ۳. تفاوت LoRa و LoRaWAN؛ پارامترهای رادیویی (Slide 45)

- **LoRa:** فناوری مدولاسیون/ارتباط رادیویی؛ می‌تواند در کاربردهای نقطه‌به‌نقطه هم به‌کار رود.
- **LoRaWAN:** پروتکل و معماری شبکه شامل دستگاه‌ها، Gateway، مدیریت اتصال و Network Server؛ **دستگاه LoRaWAN مستقیماً MQTT را روی رابط رادیویی اجرا نمی‌کند**.
- **SF (Spreading Factor):** افزایش آن در شرایط قابل مقایسه معمولاً حساسیت لینک را بهتر، اما نرخ داده را کمتر و Time on Air را بیشتر می‌کند.
- **BW (Bandwidth):** پهنای باند بالاتر معمولاً انتقال سریع‌تر با حساسیت کمتر ایجاد می‌کند؛ سایر پارامترها نیز مؤثرند.
- **CR (Coding Rate):** افزونگی بیشتر می‌تواند به تحمل خطا کمک کند، اما زمان اشغال کانال را افزایش می‌دهد.

**Time on Air، مصرف باتری، ظرفیت شبکه و مقررات فرکانسی منطقه** را با هم ارزیابی کنید. برای این پروژه SF/BW/CR یا باند فرکانسی قطعی پیشنهاد نمی‌کنیم، چون منطقه قانونی، ماژول رادیویی و وضعیت محیط هنوز تعیین نشده‌اند.

### ۴. کلاس‌های LoRaWAN (Slide 46)

| کلاس | رفتار دریافت Downlink | کاربرد متداول |
|---|---|---|
| **A** | دو پنجره دریافت کوتاه پس از هر Uplink | سنسورهای کم‌مصرف و باتری‌خور |
| **B** | علاوه بر Class A، پنجره‌های زمان‌بندی‌شده با Beacon | دریافت دوره‌ای با زمان‌بندی مشخص |
| **C** | دریافت تقریباً پیوسته، به‌جز هنگام ارسال | دستگاه‌های دارای برق ثابت و نیاز به تأخیر کمتر |

Class بالاتر لزوماً به معنی برد رادیویی بیشتر نیست؛ تفاوت اصلی در **آماده‌بودن برای دریافت، تأخیر Downlink و انرژی مصرفی** است.

### ۵. RAK2287 Gateway و ChirpStack (Slide 47)

**RAK2287** یک *LoRaWAN Concentrator Module* است، نه Gateway کامل. برای ساخت Gateway به Host سازگار (مثلاً Raspberry Pi با HAT/رابط مناسب نسخه انتخابی)، آنتن و باند منطقه‌ای صحیح، تغذیه، نرم‌افزار Packet Forwarder و **IP Backhaul** نیاز داریم. نسخه‌های رابط ماژول یکسان نیستند؛ سازگاری SPI/USB و HAT را از مستندات همان مدل بررسی کنید.

```text
LoRaWAN End Device(s) → LoRa Radio → RAK2287 + Gateway Host
                                           ↓  IP Backhaul
                                 Packet Forwarder / Bridge
                                           ↓
                                  ChirpStack Network Server
                                           ↓  Application Integration
                                    MQTT / Backend / Dashboard
```

**ChirpStack** مدیریت شبکه و دستگاه‌های LoRaWAN را انجام می‌دهد و می‌تواند از طریق Integration داده را به برنامه‌های MQTT برساند. Topicهای MQTT مربوط به ChirpStack الزاماً همان `iot/room-01/telemetry` پروژه Wi-Fi ما نیستند؛ برای یکپارچه‌سازی نهایی ممکن است تبدیل Payload و Topic لازم باشد. **MQTT Broker، Gateway و LoRaWAN Network Server سه نقش متفاوت دارند.**

### ۶. تصمیم نهایی بر اساس Use Case (Slide 48)

| سناریو | انتخاب اولیه قابل بررسی | پیش‌شرط اصلی |
|---|---|---|
| پایش اتاق‌ها با شبکه محلی موجود | **Wi-Fi** | پوشش پایدار و تغذیه مناسب |
| گلخانه دورافتاده با پوشش اپراتور | **Cellular 2G/4G یا نوع مناسب LTE** | پوشش واقعی، مودم/آنتن سازگار و هزینه داده |
| سنسورهای متعدد، پیام‌های کوچک، کار با باتری | **LoRaWAN Class A** | پوشش رادیویی، Gateway، Backhaul و ظرفیت شبکه |
| ارسال حجم زیاد داده یا Downlink پرتعداد | **بررسی Cellular/Wi-Fi و معماری جایگزین** | نیاز نرخ داده و تأخیر؛ LoRaWAN معمولاً انتخاب مناسبی برای حجم بالا نیست |

**چک‌لیست قبل از استقرار واقعی:** تست پوشش در محل، بررسی محدودیت‌های قانونی باند و توان، بودجه باتری و توان پیک، اندازه و تعداد پیام‌ها، تأخیر قابل قبول، امنیت و نگهداری کلیدها، مسیر Backhaul، هزینه کل مالکیت و برنامه بازیابی هنگام قطع ارتباط. بدون این داده‌ها، نمی‌توان برد، مصرف انرژی، هزینه یا کیفیت سرویس را به‌صورت قطعی ادعا کرد.

**خروجی آموزشی:** دانشجو بتواند بین Wi-Fi، Cellular و LoRaWAN بر اساس نیاز واقعی پروژه استدلال کند و مسیر معماری داده را رسم کند؛ نه اینکه یک راه‌اندازی LoRaWAN یا 4G انجام‌شده را مشاهده کرده باشد.
