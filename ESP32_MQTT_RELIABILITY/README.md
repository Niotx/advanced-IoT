# ESP32 MQTT Reliability — DHT22 + OLED + Raspberry Pi

در این مثال مستقل برای **Arduino IDE**، پروژه `ESP32_MQTT_PUBLISH` را یک مرحله مقاوم‌تر می‌کنیم: ESP32 همچنان داده DHT22 را روی SSD1306 نمایش می‌دهد، اما در زمان قطع Wi-Fi یا Mosquitto داده‌ها را در **یک صف محدود** نگه می‌دارد و پس از بازیابی اتصال، برای ارسال دوباره تلاش می‌کند. زمان اندازه‌گیری در صورت در دسترس بودن NTP به پیام اضافه می‌شود.

> **هدف آموزشی:** طراحی رفتار قابل پیش‌بینی هنگام قطعی شبکه. **تضمین تحویل بدون اتلاف نداریم:** `PubSubClient` برای Publish از **MQTT QoS 0** استفاده می‌کند؛ حتی بازگشت موفق `publish()` به معنی تأیید ذخیره پیام در Broker نیست. ممکن است پیام از دست برود یا پس از ریست دوباره ارسال شود. این نمونه جایگزین یک Data Logger صنعتی یا پایگاه داده نیست.

## فایل‌ها

```text
ESP32_MQTT_RELIABILITY/
├── ESP32_MQTT_RELIABILITY.ino
├── secrets.h.example
├── .gitignore
└── README.md
```

`secrets.h` را بعد از کپی‌کردن الگو **فقط روی رایانه خودتان** ایجاد کنید و در GitHub قرار ندهید.

## سخت‌افزار و اتصالات

همان قطعات مثال اول: **ESP32 DevKit V1، DHT22، OLED SSD1306 (128×64, I2C)**.

| قطعه | اتصال به ESP32 |
|---|---|
| DHT22 DATA | GPIO4 |
| DHT22 VCC / GND | 3.3V / GND |
| OLED SDA / SCL | GPIO21 / GPIO22 |
| OLED VCC / GND | 3.3V / GND |

آدرس OLED در کد `0x3C` است. در سنسور **خام** DHT22 معمولاً باید مقاومت Pull-up حدود `10kΩ` بین DATA و VCC داشته باشید؛ برخی ماژول‌ها آن را روی برد دارند. برای جزئیات سیم‌کشی، [مثال اولیه](../ESP32_DHT22_OLED/README.md) را ببینید.

## پیش‌نیازهای نرم‌افزاری

- **Arduino IDE** و بسته **ESP32 by Espressif Systems** (با پشتیبانی از `LittleFS.h`).
- Library Manager: **DHT sensor library by Adafruit**، **Adafruit Unified Sensor**، **Adafruit GFX Library**، **Adafruit SSD1306** و **PubSubClient**.
- کتابخانه‌های `WiFi.h`، `Wire.h` و `LittleFS.h` همراه بسته برد ESP32 تأمین می‌شوند؛ به یک LittleFS قدیمیِ مجزا نیاز ندارید.
- Raspberry Pi با Mosquitto، Listener روی شبکه محلی، کاربر دارای رمز و مجوز دسترسی از ESP32. ابتدا [راهنمای Broker](../RaspberryPi_MQTT_BROKER/README.md) را انجام دهید.
- برای دریافت زمان واقعی از سرورهای NTP تنظیم‌شده، دسترسی ESP32 به DNS و سرویس زمان لازم است؛ **بدون NTP، سنجش و MQTT همچنان کار می‌کنند** اما `measured_at_unix` برابر `null` خواهد بود.
- در **Tools → Partition Scheme** طرحی انتخاب کنید که پارتیشن فایل‌سیستم داشته باشد؛ نام گزینه با نسخه بسته ESP32 و حافظه فلش برد متفاوت است.

## ۱. آماده‌سازی پروژه

1. پوشه `ESP32_MQTT_RELIABILITY` را بدون تغییر نام باز کنید؛ اسم پوشه و Sketch باید یکسان باشد.
2. فایل `secrets.h.example` را **کپی** کرده و کپی را `secrets.h` بنامید.
3. مقادیر `WIFI_SSID`، `WIFI_PASSWORD`، `MQTT_HOST`، `MQTT_PORT`، `MQTT_USERNAME` و `MQTT_PASSWORD` را با مقادیر واقعی شبکه و حساب آزمایشگاهی خود جایگزین کنید. `MQTT_HOST` آدرس **Raspberry Pi** است.
4. **Partition Scheme** دارای فایل‌سیستم را بررسی کنید. تغییر طرح پارتیشن می‌تواند اطلاعات ذخیره‌شده را پاک یا غیرقابل دسترس کند.
5. اگر نمونه MQTT قبلی را هم روی دستگاه دیگری اجرا می‌کنید، `DEVICE_ID` و Topicها را برای هر دستگاه جدا کنید؛ دو کلاینت MQTT با شناسه یکسان ممکن است پی‌درپی اتصال یکدیگر را قطع کنند.
6. فایل `ESP32_MQTT_RELIABILITY.ino` را در Arduino IDE باز کنید، Board و Port را انتخاب و Upload کنید.
7. **Serial Monitor** را روی `115200 baud` قرار دهید.

> **اولین استفاده از LittleFS:** برای جلوگیری از پاک‌شدن ناخواسته داده، مقدار `FORMAT_LITTLEFS_ON_MOUNT_FAILURE` در کد به‌صورت پیش‌فرض `false` است. اگر فایل‌سیستم تازه و خالی است و Mount شکست خورد، پس از اطمینان از اینکه **هیچ داده‌ای برای حفظ‌کردن ندارید**، می‌توانید موقتاً آن را `true` کنید و یک‌بار Upload/Run انجام دهید؛ سپس دوباره `false` کنید. فعال‌کردن این گزینه ممکن است در صورت شکست Mount، محتوای قبلی فایل‌سیستم را پاک کند. اگر Mount موفق نشود، نمونه با **بافر RAM** کار می‌کند، اما بازیابی پس از خاموشی امکان‌پذیر نیست.

### امنیت تنظیمات

فایل `.gitignore` از ثبت تصادفی `secrets.h` با Git جلوگیری می‌کند، اما هنگام آپلود دستی از وب GitHub باید خودتان آن را کنار بگذارید. **رمز واقعی را هنگام ضبط صفحه نمایش ندهید**. این نمونه روی **MQTT/TCP پورت 1883 بدون TLS** است؛ فقط در LAN آزمایشگاهی مورداعتماد اجرا کنید و پورت را در اینترنت عمومی باز نکنید. TLS در بخش Security دوره اضافه می‌شود.

## ۲. چه قابلیت‌هایی اضافه شده‌اند؟

| قابلیت | رفتار این مثال |
|---|---|
| پایش محلی | خواندن DHT22 هر حدود `2500 ms` و نمایش روی OLED؛ مستقل از وجود Broker |
| مدیریت اتصال | تلاش Wi-Fi حدود هر ۱۰ ثانیه و MQTT حدود هر ۵ ثانیه؛ بدون `while` بی‌نهایت |
| مدیریت خطای سنسور | نمایش `Sensor Error` و جلوگیری از افزودن داده نامعتبر به صف |
| بافر RAM | حداکثر **۱۲۰ اندازه‌گیری**، حدود ۵ دقیقه در فاصله ۲.۵ ثانیه؛ هنگام پرشدن قدیمی‌ترین مورد حذف می‌شود |
| ذخیره در LittleFS | ذخیره دوره‌ای **Snapshot** صف هنگام قطع MQTT، تقریباً هر ۳۰ ثانیه؛ بازیابی Snapshot پس از ریست |
| ارسال مجدد | تلاش برای ارسال داده‌های قدیمی‌تر پیش از جدیدترها پس از برقراری MQTT |
| NTP | ذخیره Unix time (UTC) در لحظه نمونه‌برداری **اگر ساعت همگام شده باشد** |
| Logging | پیام‌های `[INFO]`، `[WARN]` و `[ERROR]` روی Serial Monitor؛ **Remote Logging در این کد پیاده نشده** |
| وضعیت MQTT | انتشار retained `online` و تنظیم retained Last Will برابر `offline` |

### چرا LittleFS، و جایگاه SPIFFS و NVS چیست؟

در سرفصل دوره **SPIFFS / NVS** هم مطرح‌اند. **NVS** برای تنظیمات و مقادیر کوچک کلید/مقدار مناسب‌تر است؛ **SPIFFS** و **LittleFS** فایل‌سیستم‌های فلش برای نگهداری فایل هستند. در **این پیاده‌سازی** از LittleFS برای Snapshot صف استفاده شده است. تفاوت گزینه‌ها را هنگام تدریس توضیح می‌دهیم؛ ادعا نمی‌کنیم که SPIFFS یا NVS هم در همین کد پیاده‌سازی شده‌اند.

**محدودیت‌های مهم:** تلاش TCP/MQTT یا عملیات Flash هنوز می‌توانند برای مدتی کوتاه Blocking باشند. فاصله نمونه‌برداری در این شرایط تضمین سختِ زمانی ندارد. Snapshot هر ۳۰ ثانیه نوشته می‌شود؛ بنابراین در قطع ناگهانی برق، اندازه‌گیری‌های ثبت‌شده پس از آخرین Snapshot ممکن است از بین بروند. حتی داده Snapshotشده با QoS 0 ممکن است به‌طور قطعی به Broker نرسد. از نوشتن بی‌وقفه در Flash خودداری می‌کنیم تا سایش حافظه کمتر شود، اما این سیاست هم حد و مرز دارد.

## ۳. موضوعات MQTT و Payload

```text
iot/room-01/telemetry
iot/room-01/status
```

**نمونه ساختگی صرفاً برای نمایش قالب پیام** (عددها اندازه‌گیری واقعی نیستند):

```json
{
  "device_id": "esp32-room-01",
  "boot_id": "3a19b0ff",
  "sequence": 16,
  "temperature": 24.6,
  "humidity": 42.8,
  "uptime_ms": 152000,
  "measured_at_unix": 1780000000,
  "buffered": true
}
```

| فیلد | معنی |
|---|---|
| `device_id` | شناسه دستگاه |
| `boot_id` و `sequence` | شناسایی یک اندازه‌گیری در یک نوبت روشن‌بودن دستگاه؛ برای تشخیص تکراری‌ها کاربرد دارد |
| `temperature` / `humidity` | دما بر حسب °C و رطوبت نسبی بر حسب درصد |
| `uptime_ms` | زمان گذشته از روشن‌شدن ESP32 در هنگام اندازه‌گیری؛ **ساعت واقعی نیست** و پس از ریست از نو شروع می‌شود |
| `measured_at_unix` | ثانیه Unix در **لحظه اندازه‌گیری**، یا `null` اگر هنوز زمان معتبر از NTP نداریم |
| `buffered` | `true` یعنی نمونه در صف هنگام قطعی/انتظار بوده یا از Flash بازیابی شده است |

ساختار قدیمی `device_id`، `temperature`، `humidity` و `uptime_ms` حفظ شده؛ بنابراین Subscriber ساده قبلی می‌تواند همچنان مقدارهای اصلی را بخواند و فیلدهای اضافه را نادیده بگیرد.

**نکته زمان:** اگر سنسور پیش از همگام‌سازی NTP نمونه گرفته باشد، زمان واقعی آن نمونه را بعداً جعل یا حدس نمی‌زنیم؛ همان `null` باقی می‌ماند. برای نمونه‌های ذخیره‌شده هم زمان **اندازه‌گیری** ملاک است، نه زمان ارسال مجدد.

## ۴. آزمایش مرحله‌به‌مرحله

### آزمایش A — کارکرد عادی

1. سرویس Mosquitto و اتصال شبکه را بررسی کنید.
2. برنامه را اجرا کنید؛ انتظار دارید `[INFO] Wi-Fi connected`، `[INFO] MQTT connected` و پیام‌های DHT22 را ببینید.
3. روی OLED مقدارها و نشانگرهای `W` (Wi-Fi)، `M` (MQTT) و `Q` (تعداد پیام در صف) را بررسی کنید.
4. برای مشاهده MQTT، از [Python Subscriber](../RaspberryPi_MQTT_SUBSCRIBER/README.md) یا MQTT Explorer استفاده کنید.

برای تست سریع با ابزار خط فرمان، با **حساب آزمایشگاهی** (رمز نمونه را جایگزین کنید) روی Raspberry Pi اجرا کنید:

```bash
mosquitto_sub -h localhost -p 1883 -u iot_device -P 'REPLACE_WITH_TEST_PASSWORD' -t 'iot/room-01/#' -v
```

قرار دادن رمز حقیقی در آرگومان‌های CLI می‌تواند آن را در تاریخچه Shell یا فهرست پردازش‌ها آشکار کند؛ برای ضبط از رمز آزمایشی استفاده کنید و آن را بعداً تغییر دهید.

### آزمایش B — قطع Broker و رشد بافر

در Raspberry Pi:

```bash
sudo systemctl stop mosquitto
```

حداقل **۴۰ ثانیه** صبر کنید. روی Serial Monitor به دنبال تلاش اتصال مجدد، افزایش `queue` و پیام `Saved ... buffered readings to flash` بگردید. روی OLED سنسور باید همچنان کار کند. اگر LittleFS Mount نشده باشد، پیام هشدار مربوط را خواهید دید.

### آزمایش C — بازیابی پس از ریست دستگاه (اختیاری)

**فقط پس از مشاهده پیام موفقیت‌آمیز ذخیره Snapshot** و با Broker همچنان خاموش، ESP32 را Reset کنید. در خروجی Serial باید `Restored ... unsent readings from LittleFS` مشاهده شود. داده‌هایی که بعد از آخرین Snapshot ثبت شده‌اند ممکن است برنگردند؛ این رفتار محدودیت طراحی مثال است.

### آزمایش D — اتصال مجدد و تخلیه صف

Broker را دوباره فعال کنید:

```bash
sudo systemctl start mosquitto
```

پیام‌های `MQTT connected` و `MQTT publish (queued left ...)` را دنبال کنید. وقتی صف کاملاً تخلیه شود، فایل Snapshot قبلی پاک می‌شود. در MQTT Explorer یا Subscriber، فیلدهای `boot_id`، `sequence`، `buffered` و `measured_at_unix` را بررسی کنید.

> **تفسیر صحیح آزمون:** تخلیه‌شدن صف در ESP32 الزاماً ثابت نمی‌کند همه پیام‌ها در Subscriber ذخیره شده‌اند. برای تضمین تحویل باید QoS، تأیید سمت سرور، شناسایی پیام تکراری و طراحی ذخیره‌سازی را عمیق‌تر بررسی کنیم.

### آزمایش E — قطع Wi-Fi یا خطای سنسور

Wi-Fi را موقتاً قطع کنید تا تفاوت **وضعیت Wi-Fi** و **MQTT** مشخص شود. برای آزمون خطای سنسور، با **قطع تغذیه سخت‌افزار** و بررسی مجدد سیم‌کشی، شرایط نامعتبر را ایجاد کنید؛ سیم‌کشی را زیر برق دست‌کاری نکنید. هیچ داده نامعتبری نباید Publish یا وارد صف شود.

## ۵. رفتارهای خطا و محدودیت‌ها

| مشاهده | احتمال / اقدام |
|---|---|
| `LittleFS not mounted` | طرح پارتیشن فایل‌سیستم ندارد یا فایل‌سیستم آماده نیست؛ طبق بخش ۱ بررسی کنید. **بدون بررسی، فرمت نکنید**. |
| `Wi-Fi connection attempt` تکرار می‌شود | SSID، رمز، محدوده سیگنال و تغذیه را بررسی کنید. ESP32 DevKit V1 از Wi-Fi ‏2.4GHz استفاده می‌کند. |
| `MQTT connect failed` | IP، Listener، UFW، حساب MQTT و اجرای Mosquitto را بررسی کنید. |
| `NTP synchronized` نمایش داده نمی‌شود | DNS، دسترسی به NTP و زمان شبکه را بررسی کنید؛ `measured_at_unix` ممکن است `null` بماند. |
| `Buffer full` | قطعی طولانی‌تر از ظرفیت صف است؛ قدیمی‌ترین خواندن حذف می‌شود و تعداد حذف‌ها در Diagnostics می‌آید. |
| `snapshot write/rename failed` | حافظه فلش، پارتیشن و دسترسی به فایل‌سیستم را بررسی کنید؛ تا رفع مشکل فقط RAM قابل اتکاست. |
| پیام‌های قدیمی تکرار می‌شوند | در Snapshot و QoS 0 وضعیت تحویل قطعی معلوم نیست؛ `boot_id + sequence` برای تشخیص تکراری‌ها کمک می‌کند. |
| OLED پیدا نمی‌شود | I2C، تغذیه و آدرس `0x3C` را بررسی کنید؛ نمونه خطا را گزارش می‌کند اما خواندن سنسور و MQTT را متوقف نمی‌کند. |

## ۶. چه چیزهایی هنوز پیاده نشده‌اند؟

- **MQTT over TLS** و مدیریت Certificate؛ موضوع بخش امنیت دوره.
- تضمین تحویل end-to-end، ACK کاربردی، نگهداری داده در پایگاه داده یا حذف تکرار در سمت سرور.
- Logging مرکزی، داشبورد و پایش عملیاتی؛ Logging فعلاً صرفاً روی Serial است.
- FreeRTOS Task / Queue / Semaphore؛ بازآرایی در بخش Firmware Architecture انجام می‌شود.
- پیاده‌سازی MessagePack و Protobuf؛ در این بخش فقط از نظر مفهوم و کاربرد با JSON مقایسه می‌شوند.
- OTA و Rollback؛ در بخش نگهداری آموزش داده می‌شوند.
