## ۱. اولین نمونه: اندازه‌گیری و نمایش محلی

**مسئله:** اندازه‌گیری دما و رطوبت محیط، بدون نیاز به شبکه.

**سخت‌افزار:** ESP32 DevKit V1، سنسور DHT22 و نمایشگر OLED SSD1306 با ارتباط I2C.

**مراحل:**

1. مطابق جدول اتصالات و تصویر سیم‌کشی، قطعات را وصل کنید.
2. کتابخانه‌های موردنیاز را در Arduino IDE نصب کنید.
3. فایل `ESP32_DHT22_OLED.ino` را باز و روی ESP32 بارگذاری کنید.
4. خروجی OLED و Serial Monitor را بررسی کنید.
5. خطای خواندن سنسور را نیز آزمایش کنید.

**کد، اتصالات و راهنمای اجرا:** [ESP32_DHT22_OLED](./ESP32_DHT22_OLED/README.md)

**خروجی مورد انتظار:** مقادیر دما و رطوبت به‌صورت محلی نمایش داده می‌شوند؛ در صورت نامعتبر بودن خواندن سنسور، پیام خطا ظاهر می‌شود.

## ۲. مسئله ارتباط از راه دور

**نیاز جدید:** کاربر باید بتواند داده‌های سنسور را از دستگاه دیگری دریافت کند.

برای انتخاب فناوری ارتباط، الگوهای **Request/Response** و **Publish/Subscribe** و گزینه‌های HTTP/HTTPS، MQTT و CoAP را مقایسه می‌کنیم.

**تصمیم معماری این پروژه:** برای تله‌متری دوره‌ای، MQTT را با یک Broker محلی روی Raspberry Pi انتخاب می‌کنیم. این انتخاب مختص نیازهای پروژه است؛ HTTP/HTTPS و CoAP در سناریوهای دیگر همچنان می‌توانند مناسب باشند.

> تا این مرحله، اتصال MQTT هنوز در کد نمونه اولیه پیاده‌سازی نشده است.

## ۳. آماده‌سازی Raspberry Pi و دسترسی از راه دور

**مسئله:** برای اجرای سرویس‌های سمت شبکه، ابتدا به یک Raspberry Pi آماده و قابل مدیریت نیاز داریم.

**سخت‌افزار:** Raspberry Pi 4 Model B (4GB RAM)، منبع تغذیه مناسب، کارت microSD و اتصال شبکه.

### اجرای سریع

1. [Raspberry Pi Imager](https://www.raspberrypi.com/software/) را روی مک نصب کنید.
2. سیستم‌عامل **Raspberry Pi OS Lite (64-bit)** را برای Raspberry Pi 4 انتخاب کنید.
3. در بخش تنظیمات اولیه Imager، نام میزبان، حساب کاربری، Wi-Fi و **SSH** را پیکربندی کنید.
4. کارت را در Raspberry Pi قرار دهید و دستگاه را روشن کنید.
5. در ترمینال مک، با نام کاربری و میزبان **واقعیِ تنظیم‌شده توسط خودتان** وصل شوید:

```bash
ssh iotuser@iot-pi.local
```

در این مثال `iotuser` و `iot-pi` صرفاً نام‌های نمونه هستند. اگر `*.local` در شبکه شناسایی نشد، IP دستگاه را از فهرست دستگاه‌های متصل در روتر پیدا کنید.

بعد از اتصال، IP فعلی را مشاهده کنید:

```bash
hostname -I
```

در ادامه، متناسب با شبکه خودتان، آدرس پایدار (**DHCP Reservation** یا **Static IP**) را تنظیم کنید. ورود با **SSH Key** را آزمایش کنید و سپس دسترسی SSH را سخت‌سازی کنید: غیرفعال‌کردن ورود مستقیم **root**، غیرفعال‌کردن احراز هویت با رمز پس از تأیید کلید، تغییر اختیاری پورت SSH و نصب **UFW** برای محدودکردن پورت‌های ورودی. **قبل از فعال‌کردن UFW یا تغییر پورت، دسترسی SSH جدید را مجاز کنید تا اتصال قطع نشود.**

تمام دستورها، نکات بازیابی دسترسی و آزمون‌های این بخش در راهنمای مستقل زیر قرار دارند.

**راهنمای کامل، دستورات، آزمون‌ها و رفع خطا:** [RaspberryPi_SSH_SETUP](./RaspberryPi_SSH_SETUP/README.md)

**خروجی مورد انتظار:** اتصال قابل تکرار از مک به Raspberry Pi در شبکه محلی، ترجیحاً با SSH Key.

## ۴. راه‌اندازی MQTT Broker روی Raspberry Pi

**مسئله:** برای دریافت داده‌های ESP32 به یک Broker محلی نیاز داریم.

1. بسته‌های `mosquitto` و `mosquitto-clients` را نصب کنید و وضعیت سرویس را بررسی کنید.
2. با `mosquitto_sub` و `mosquitto_pub` تبادل پیام را روی خود Raspberry Pi آزمایش کنید.
3. یک کاربر MQTT ایجاد کنید و Listener شبکه محلی را با `allow_anonymous false` تنظیم کنید.
4. دسترسی TCP/1883 را در UFW **فقط برای شبکه مورداعتماد** مجاز کنید.
5. تبادل پیام از دستگاه دیگری در شبکه را با حساب مجاز تست کنید.

**تمام دستورها، خروجی مورد انتظار و رفع خطاها:** [RaspberryPi_MQTT_BROKER](./RaspberryPi_MQTT_BROKER/README.md)

**خروجی مورد انتظار:** Mosquitto روی Raspberry Pi فعال است و کلاینت‌های مجاز شبکه محلی می‌توانند پیام MQTT ارسال و دریافت کنند.

## ۵. ارسال داده DHT22 از ESP32 با MQTT

**مسئله:** داده‌های سنسور علاوه بر OLED، باید از ESP32 به Broker روی Raspberry Pi ارسال شوند.

1. طبق [راهنمای Broker](./RaspberryPi_MQTT_BROKER/README.md)، از فعال‌بودن سرویس و دسترسی حساب MQTT مطمئن شوید.
2. در [ESP32_MQTT_PUBLISH](./ESP32_MQTT_PUBLISH/README.md) کتابخانه‌ها را نصب کنید و از `secrets.h.example` یک فایل محلی `secrets.h` بسازید.
3. IP واقعی Raspberry Pi و اطلاعات Wi-Fi/MQTT را فقط در `secrets.h` وارد کنید؛ آن را در GitHub منتشر نکنید.
4. فایل `ESP32_MQTT_PUBLISH.ino` را با Arduino IDE روی ESP32 بارگذاری کنید.
5. در MQTT Explorer یا `mosquitto_sub`، پیام‌های `iot/room-01/telemetry` و `iot/room-01/status` را ببینید.

**کد کامل، دستورهای قابل کپی، خروجی مورد انتظار و رفع خطا:** [ESP32_MQTT_PUBLISH](./ESP32_MQTT_PUBLISH/README.md)

**نتیجه:** نمایش OLED محلی باقی می‌ماند و اندازه‌گیری‌های معتبر از طریق MQTT در شبکه آزمایشگاهی ارسال می‌شوند. در این نسخه هنوز زمان واقعی NTP، ذخیره داده در قطعی شبکه و TLS پیاده‌سازی نشده‌اند.

## ۶. دریافت و پردازش تله‌متری با Python

**مسئله:** پس از Publish موفق ESP32، داده باید روی Raspberry Pi در یک برنامه قابل پردازش دریافت شود.

1. مطابق [راهنمای Broker](./RaspberryPi_MQTT_BROKER/README.md)، از فعال‌بودن سرویس Mosquitto مطمئن شوید.
2. با [`ESP32_MQTT_PUBLISH`](./ESP32_MQTT_PUBLISH/README.md) داده‌های دما و رطوبت را Publish کنید.
3. در [`RaspberryPi_MQTT_SUBSCRIBER`](./RaspberryPi_MQTT_SUBSCRIBER/README.md)، محیط Python و کتابخانه `paho-mqtt` را آماده کنید.
4. اسکریپت `subscriber.py` را با حساب MQTT اجرا کنید و پیام‌های `telemetry` و `status` را مشاهده کنید.
5. داده دریافت‌شده را با خروجی OLED و Serial Monitor مقایسه کنید؛ پیام وضعیت `offline` را هم در سناریوی قطع ESP32 آزمایش کنید.

**کد، دستورات قابل کپی، خروجی نمونه و رفع خطا:** [RaspberryPi_MQTT_SUBSCRIBER](./RaspberryPi_MQTT_SUBSCRIBER/README.md)

**خروجی مورد انتظار:** پیام JSON به مقادیر دما، رطوبت، شناسه دستگاه و `uptime_ms` تبدیل می‌شود. این مرحله **ذخیره‌سازی، داشبورد یا Timestamp واقعی** اضافه نمی‌کند؛ آن‌ها در مراحل بعد بررسی می‌شوند.

## ۷. پایداری سیستم هنگام قطع ارتباط (Reliability & Data Management)

**مسئله:** وقتی Wi-Fi یا MQTT Broker در دسترس نیست، اندازه‌گیری محلی باید ادامه پیدا کند و برای داده‌های ارسال‌نشده سیاست مشخصی داشته باشیم.

1. ابتدا نسخه ساده [ESP32_MQTT_PUBLISH](./ESP32_MQTT_PUBLISH/README.md) را اجرا و ارسال پیام را تأیید کنید.
2. در [ESP32_MQTT_RELIABILITY](./ESP32_MQTT_RELIABILITY/README.md) تنظیمات اتصال را در یک فایل محلی `secrets.h` بسازید و Sketch مستقل آن را Upload کنید.
3. با قطع موقت Mosquitto، ادامه کار DHT22 و OLED، تلاش اتصال مجدد و افزایش صف RAM را بررسی کنید.
4. در صورت آماده بودن LittleFS، ذخیره دوره‌ای Snapshot و بازیابی صف پس از Reset را آزمایش کنید.
5. Broker را دوباره فعال و ارسال مجدد داده‌های صف را مشاهده کنید. تفاوت `uptime_ms` با `measured_at_unix` و نقش NTP را توضیح دهید.
6. Logهای `[INFO]`، `[WARN]` و `[ERROR]` را بررسی کنید. درباره تفاوت JSON با MessagePack و Protobuf، انتخاب LittleFS در مقایسه با SPIFFS/NVS و محدودیت‌های بافر/Flash به‌صورت مفهومی بحث کنید.

**کد، راه‌اندازی، آزمایش‌ها و رفع خطا:** [ESP32_MQTT_RELIABILITY](./ESP32_MQTT_RELIABILITY/README.md)

**نتیجه مورد انتظار:** محصول هنگام قطع Broker پایش محلی را ادامه می‌دهد و در حد ظرفیت صف برای ارسال مجدد تلاش می‌کند. **این مثال تحویل تضمین‌شده یا ثبت دائمی همه داده‌ها نیست**؛ تله‌متری هنوز با QoS 0 و بدون TLS منتشر می‌شود. Remote Logging و FreeRTOS هم هنوز پیاده‌سازی نشده‌اند.

## ۸. معماری Firmware و FreeRTOS — Slides 31–34

**مسئله:** با زیادشدن مسئولیت‌های Firmware، می‌خواهیم خواندن سنسور و نمایش اطلاعات را در دو وظیفه جدا مدیریت کنیم و به‌شکل ایمن بین آن‌ها داده منتقل کنیم.

1. ابتدا تفاوت معماری **Loop-Based** و برنامه زمان‌بندی‌شده یا **Event-Driven** را مرور کنید؛ FreeRTOS برای هر پروژه‌ای الزامی نیست.
2. مثال مستقل [ESP32_FreeRTOS_SENSOR_TASKS](./ESP32_FreeRTOS_SENSOR_TASKS/README.md) را با اتصالات فعلی DHT22 و OLED اجرا کنید.
3. مسیر **SensorTask → FreeRTOS Queue → DisplayTask** را روی OLED و Serial Monitor بررسی کنید.
4. با فعال‌کردن `DEMO_SLOW_DISPLAY`، پرشدن Queue و سیاست حذف نمونه جدید را آزمایش کنید؛ سپس گزینه را غیرفعال کنید.
5. نقش **Mutex** در Serial Logging و تفاوت آن با **Binary Semaphore** را توضیح دهید. خطای سنسور را نیز آزمایش کنید.

**کد کامل، کتابخانه‌ها، اتصالات، آزمایش‌ها و رفع خطا:** [ESP32_FreeRTOS_SENSOR_TASKS](./ESP32_FreeRTOS_SENSOR_TASKS/README.md)

**نتیجه مورد انتظار:** دو Task جدا برای سنسور و نمایشگر با یک Queue محدود و Mutex برای Logها کار می‌کنند. این مثال **MQTT یا Reliability قبلی را بازنویسی نمی‌کند** و برای یادگیری Task / Queue / Synchronization مستقل است؛ تست سخت‌افزاری نهایی لازم است.

## ۹. امنیت IoT — MQTT over TLS & Access Control (Slides 35–38)

**مسئله:** تا اینجا ESP32 با MQTT معمولی روی پورت ۱۸۸۳ پیام می‌فرستاد. حالا لازم است **Broker به‌صورت معتبر شناسایی شود، مسیر MQTT رمزنگاری شود و هر کاربر تنها به Topicهای مجاز دسترسی داشته باشد**.

1. ابتدا تهدیدهای شنود، ورود غیرمجاز، پیام جعلی و افشای اطلاعات اتصال را بررسی کنید.
2. با [TLS_SETUP روی Raspberry Pi](./RaspberryPi_MQTT_BROKER/TLS_SETUP.md)، CA آزمایشگاهی و گواهی اختصاصی Broker با SAN منطبق با IP/DNS بسازید؛ **کلیدهای خصوصی را وارد GitHub نکنید**.
3. در Mosquitto دو کاربر مستقل و یک ACL با دسترسی محدود به Topicهای `iot/room-01/telemetry` و `iot/room-01/status` ایجاد کنید.
4. Listener امن TCP/8883 را **قبل از محدودکردن ۱۸۸۳** راه‌اندازی کنید و اعتبار CA، اتصال و ACL را با ابزارهای خط فرمان آزمایش کنید.
5. نمونه مستقل [ESP32_MQTT_TLS](./ESP32_MQTT_TLS/README.md) را اجرا کنید؛ از `secrets.h.example` یک `secrets.h` محلی بسازید و **گواهی عمومی CA** را در آن قرار دهید.
6. پس از تأیید اتصال امن، دسترسی شبکه‌ایِ ۱۸۸۳ را به localhost محدود کنید و Firewall را با حفظ دسترسی SSH بازبینی کنید.

**راهنمای Broker و تولید گواهی:** [RaspberryPi_MQTT_BROKER/TLS_SETUP.md](./RaspberryPi_MQTT_BROKER/TLS_SETUP.md)

**کد و راهنمای ESP32:** [ESP32_MQTT_TLS](./ESP32_MQTT_TLS/README.md)

**خروجی مورد انتظار:** ارتباط MQTT با TLS و اعتبارسنجی گواهی Broker برقرار می‌شود و حساب ESP32 فقط مجوز Publish روی Topicهای خود را دارد. **این نمونه Mutual TLS، ذخیره‌سازی آفلاین یا QoS تحویل تضمین‌شده ارائه نمی‌کند.** فایل‌های Credential واقعی و Private Keyها هیچ‌وقت بخشی از GitHub نیستند. اتصال روی سخت‌افزار واقعی نیازمند آزمون نهایی است.

## ۱۰. OTA و نگهداری از راه دور — Slides 39–42

**مسئله:** بعد از نصب ESP32 و Raspberry Pi در محیط واقعی، چگونه بدون اتصال مکرر USB، Firmware را به‌روزرسانی کنیم و سرویس‌های Raspberry Pi را قابل مدیریت نگه داریم؟

1. با [ESP32_OTA_UPDATE](./ESP32_OTA_UPDATE/README.md)، پس از انتخاب Partition Scheme مناسب، نسخه `1.0.0` را **یک بار با USB** روی ESP32 نصب کنید.
2. در شبکه محلی مورداعتماد، نسخه را به `1.1.0` تغییر دهید و از طریق `ArduinoOTA` آپلود کنید؛ روی OLED و Serial تغییر نسخه و ادامه خواندن DHT22 را بررسی کنید.
3. تفاوت **دو OTA Partition** با **Rollback خودکار همراه با Health Check** را بررسی کنید. **این مثال ArduinoOTA، Signed OTA و Rollback تولیدی پیاده نمی‌کند.**
4. با [RaspberryPi_MAINTENANCE](./RaspberryPi_MAINTENANCE/README.md) وضعیت Mosquitto، Logهای `journalctl`، منابع سیستم و بسته‌های قابل ارتقا با `apt` را بررسی کنید.
5. انتقال فایل با `rsync --dry-run` و سپس `rsync` را تمرین کنید؛ کاربرد Ansible برای مدیریت چند Raspberry Pi را در مثال مفهومی README ببینید.

**کد و دمو OTA:** [ESP32_OTA_UPDATE](./ESP32_OTA_UPDATE/README.md)  
**راهنمای نگهداری Raspberry Pi:** [RaspberryPi_MAINTENANCE](./RaspberryPi_MAINTENANCE/README.md)

**نتیجه مورد انتظار:** دانشجو بتواند **در LAN آزمایشگاهی** نسخه جدید Firmware را بدون USB روی ESP32 نصب و عملکرد سنسور را بعد از راه‌اندازی مجدد تأیید کند؛ و سرویس‌های Raspberry Pi را از طریق SSH بررسی کند. **این نمونه OTA برای اینترنت عمومی یا Production امن‌سازی نشده** و قابلیت‌های MQTT/TLS یا Buffering مثال‌های قبل را در خود ادغام نمی‌کند. اجرای واقعی روی سخت‌افزار هنوز نیاز به آزمون نهایی دارد.

## ۱۱. ارتباطات فراتر از Wi-Fi — بخش دهم دوره (Slides 43–48)

**مسئله:** تا اینجا ESP32 و Raspberry Pi در یک شبکه محلی دارای Wi-Fi کار می‌کردند. حالا فرض کنید یک سنسور دما و رطوبت در مزرعه‌ای دور از Access Point نصب شده و فقط هر چند دقیقه یک پیام کوچک ارسال می‌کند. چه فناوری ارتباطی با محدودیت پوشش، انرژی، هزینه و زمان پاسخ‌گویی سازگارتر است؟

> **وضعیت این بخش:** محتوای اسلایدهای ۴۳ تا ۴۸ **مفهومی و معماری** است. در این دوره برای Cellular یا LoRaWAN کد اجرایی، آزمایش برد، اندازه‌گیری برد/توان یا راه‌اندازی Gateway انجام نداده‌ایم. اعداد عملکردی بدون تجهیزات و تست میدانی گزارش نمی‌شوند؛ **پوشه نمونه اجرایی جداگانه‌ای هم برای این بخش وجود ندارد**.

### ۱. مسئله انتخاب ارتباط (Slide 43)

قبل از انتخاب فناوری، نیازمندی‌ها را مشخص کنید: موقعیت نصب و پوشش واقعی، منبع تغذیه (باتری یا برق ثابت)، اندازه و فاصله زمانی پیام‌ها، حداکثر تأخیر قابل قبول برای Downlink، تعداد دستگاه‌ها، زیرساخت موجود، هزینه اولیه و هزینه نگهداری. **LPWAN** خانواده‌ای از راهکارهای شبکه گسترده با تمرکز بر دستگاه‌های کم‌مصرف و داده کم‌حجم است؛ هر ارتباط سلولار 4G الزاماً LPWAN نیست.

### ۲. Cellular IoT: 2G / 4G (Slide 44)

در راهکار سلولار، ESP32 معمولاً با **UART** و **AT Commands** به مودم سازگار متصل می‌شود. مودم با **SIM، تنظیمات APN و آنتن مناسب** از شبکه اپراتور برای انتقال داده استفاده می‌کند؛ ESP32 به‌تنهایی مودم سلولار ندارد.

```text
DHT22 → ESP32 → UART → Cellular Modem + SIM + Antenna
                                     ↓
                            Mobile Operator Network
                                     ↓
                              Internet / Backend
```

چند دستور متداول برای **آشنایی با نقش AT Commands** (نه یک راهنمای اجرایی وابسته به مودم مشخص):

| دستور | کاربرد متداول |
|---|---|
| `AT` | آزمایش پاسخ‌دهی رابط مودم |
| `AT+CPIN?` | بررسی آماده‌بودن SIM |
| `AT+CSQ` | دریافت نشانگر کلی قدرت سیگنال؛ به‌تنهایی معیار کامل کیفیت LTE نیست |
| `AT+CREG?` / `AT+CEREG?` | بررسی وضعیت ثبت‌نام در شبکه‌های مربوط، بسته به نوع مودم و شبکه |

**قبل از خرید:** فعال‌بودن 2G/4G در محل و نزد اپراتور، باندهای فرکانسی مودم، پشتیبانی SIM/APN، سازگاری سطح ولتاژ UART، **جریان لحظه‌ای منبع تغذیه**، آنتن و هزینه اشتراک را بررسی کنید. 2G ممکن است در بعضی کشورها یا شبکه‌ها خاموش شده یا در حال خروج از سرویس باشد. گزینه‌های اختصاصی IoT سلولار مثل LTE-M و NB-IoT نیز فقط در صورت پشتیبانی واقعی اپراتور قابل بررسی‌اند.

### ۳. تفاوت LoRa و LoRaWAN؛ پارامترهای رادیویی (Slide 45)

- **LoRa:** فناوری مدولاسیون/ارتباط رادیویی؛ می‌تواند در کاربردهای نقطه‌به‌نقطه هم به‌کار رود.
- **LoRaWAN:** پروتکل و معماری شبکه شامل دستگاه‌ها، Gateway، مدیریت اتصال و Network Server؛ **دستگاه LoRaWAN مستقیماً MQTT را روی رابط رادیویی اجرا نمی‌کند**.
- **SF (Spreading Factor):** افزایش آن در شرایط قابل مقایسه معمولاً حساسیت لینک را بهتر، اما نرخ داده را کمتر و Time on Air را بیشتر می‌کند.
- **BW (Bandwidth):** پهنای باند بالاتر معمولاً انتقال سریع‌تر با حساسیت کمتر ایجاد می‌کند؛ سایر پارامترها نیز مؤثرند.
- **CR (Coding Rate):** افزونگی بیشتر می‌تواند به تحمل خطا کمک کند، اما زمان اشغال کانال را افزایش می‌دهد.

**Time on Air، مصرف باتری، ظرفیت شبکه و مقررات فرکانسی منطقه** را با هم ارزیابی کنید. برای این پروژه SF/BW/CR یا باند فرکانسی قطعی پیشنهاد نمی‌کنیم، چون منطقه قانونی، ماژول رادیویی و وضعیت محیط هنوز تعیین نشده‌اند.

### ۴. کلاس‌های LoRaWAN (Slide 46)

| کلاس | رفتار دریافت Downlink | کاربرد متداول |
|---|---|---|
| **A** | دو پنجره دریافت کوتاه پس از هر Uplink | سنسورهای کم‌مصرف و باتری‌خور |
| **B** | علاوه بر Class A، پنجره‌های زمان‌بندی‌شده با Beacon | دریافت دوره‌ای با زمان‌بندی مشخص |
| **C** | دریافت تقریباً پیوسته، به‌جز هنگام ارسال | دستگاه‌های دارای برق ثابت و نیاز به تأخیر کمتر |

Class بالاتر لزوماً به معنی برد رادیویی بیشتر نیست؛ تفاوت اصلی در **آماده‌بودن برای دریافت، تأخیر Downlink و انرژی مصرفی** است.

### ۵. RAK2287 Gateway و ChirpStack (Slide 47)

**RAK2287** یک *LoRaWAN Concentrator Module* است، نه Gateway کامل. برای ساخت Gateway به Host سازگار (مثلاً Raspberry Pi با HAT/رابط مناسب نسخه انتخابی)، آنتن و باند منطقه‌ای صحیح، تغذیه، نرم‌افزار Packet Forwarder و **IP Backhaul** نیاز داریم. نسخه‌های رابط ماژول یکسان نیستند؛ سازگاری SPI/USB و HAT را از مستندات همان مدل بررسی کنید.

```text
LoRaWAN End Device(s) → LoRa Radio → RAK2287 + Gateway Host
                                           ↓  IP Backhaul
                                 Packet Forwarder / Bridge
                                           ↓
                                  ChirpStack Network Server
                                           ↓  Application Integration
                                    MQTT / Backend / Dashboard
```

**ChirpStack** مدیریت شبکه و دستگاه‌های LoRaWAN را انجام می‌دهد و می‌تواند از طریق Integration داده را به برنامه‌های MQTT برساند. Topicهای MQTT مربوط به ChirpStack الزاماً همان `iot/room-01/telemetry` پروژه Wi-Fi ما نیستند؛ برای یکپارچه‌سازی نهایی ممکن است تبدیل Payload و Topic لازم باشد. **MQTT Broker، Gateway و LoRaWAN Network Server سه نقش متفاوت دارند.**

### ۶. تصمیم نهایی بر اساس Use Case (Slide 48)

| سناریو | انتخاب اولیه قابل بررسی | پیش‌شرط اصلی |
|---|---|---|
| پایش اتاق‌ها با شبکه محلی موجود | **Wi-Fi** | پوشش پایدار و تغذیه مناسب |
| گلخانه دورافتاده با پوشش اپراتور | **Cellular 2G/4G یا نوع مناسب LTE** | پوشش واقعی، مودم/آنتن سازگار و هزینه داده |
| سنسورهای متعدد، پیام‌های کوچک، کار با باتری | **LoRaWAN Class A** | پوشش رادیویی، Gateway، Backhaul و ظرفیت شبکه |
| ارسال حجم زیاد داده یا Downlink پرتعداد | **بررسی Cellular/Wi-Fi و معماری جایگزین** | نیاز نرخ داده و تأخیر؛ LoRaWAN معمولاً انتخاب مناسبی برای حجم بالا نیست |

**چک‌لیست قبل از استقرار واقعی:** تست پوشش در محل، بررسی محدودیت‌های قانونی باند و توان، بودجه باتری و توان پیک، اندازه و تعداد پیام‌ها، تأخیر قابل قبول، امنیت و نگهداری کلیدها، مسیر Backhaul، هزینه کل مالکیت و برنامه بازیابی هنگام قطع ارتباط. بدون این داده‌ها، نمی‌توان برد، مصرف انرژی، هزینه یا کیفیت سرویس را به‌صورت قطعی ادعا کرد.

**خروجی آموزشی:** دانشجو بتواند بین Wi-Fi، Cellular و LoRaWAN بر اساس نیاز واقعی پروژه استدلال کند و مسیر معماری داده را رسم کند؛ نه اینکه یک راه‌اندازی LoRaWAN یا 4G انجام‌شده را مشاهده کرده باشد.
