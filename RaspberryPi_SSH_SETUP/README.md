# راه‌اندازی Headless و امن Raspberry Pi با SSH — راهنمای macOS، Linux و Windows

> **پروژه آموزشی اینترنت اشیا (IoT)** | دستگاه نمونه: **Raspberry Pi 4 Model B (4GB)** | سیستم‌عامل هدف: **Raspberry Pi OS Lite (64-bit)**  
> **سطح:** مقدماتی تا متوسط | **زبان آموزش:** فارسی | **روش اجرا:** مرحله‌به‌مرحله، همراه با توضیح منطق دستورها

این README نسخه توسعه‌یافته راهنمای راه‌اندازی Raspberry Pi است. هدف این نیست که چند دستور را بدون فهمیدن کپی کنیم؛ می‌خواهیم بدانیم **هر دستور روی کدام دستگاه اجرا می‌شود، چرا اجرا می‌شود، چه تغییری ایجاد می‌کند و از کجا بفهمیم درست کار کرده است**.

این راهنما برای کامپیوتری که از آن به Raspberry Pi متصل می‌شویم، هر سه سیستم‌عامل زیر را پوشش می‌دهد:

- **macOS:** برنامه Terminal و شِل معمول `zsh` یا `bash`.
- **Linux:** برنامه Terminal و شِل معمول `bash` یا `zsh`؛ بعضی توزیع‌ها ممکن است ابزارهای شبکه متفاوتی داشته باشند.
- **Windows 10/11:** برنامه **PowerShell** به همراه **OpenSSH Client**. دستورهای ویندوز این راهنما برای PowerShell نوشته شده‌اند؛ لزوماً برای CMD، Git Bash یا WSL یکسان نیستند.

**محدوده پروژه:** نصب Raspberry Pi OS، راه‌اندازی Headless، شبکه محلی، اتصال SSH، تنظیم SSH Key، IP پایدار و سخت‌سازی اولیه SSH و فایروال. **نصب Mosquitto/MQTT Broker** مربوط به درس یا پروژه بعدی است و در اینجا انجام نمی‌شود.

## ۱. قبل از شروع: نقشه راه و واژه‌های مهم

### ۱.۱. منظور از Headless چیست؟

در روش **Headless**، Raspberry Pi را بدون مانیتور، کیبورد و ماوس جداگانه راه‌اندازی و اداره می‌کنیم. تنظیمات اولیه شبکه و SSH را هنگام نصب سیستم‌عامل انجام می‌دهیم؛ سپس از لپ‌تاپ یا رایانه خودمان به Raspberry Pi متصل می‌شویم.

```text
کامپیوتر شخصی (macOS / Linux / Windows)
                 |
                 |  شبکه محلی (Wi-Fi یا Ethernet)
                 |  ارتباط امن SSH
                 v
          Raspberry Pi 4
      Raspberry Pi OS Lite
          کاربر: iotuser
```

### ۱.۲. تفاوت SSH Client و SSH Server

- **SSH Client (کلاینت):** برنامه `ssh` روی کامپیوتر شخصی؛ درخواست اتصال را ایجاد می‌کند.
- **SSH Server (سرور):** برنامه `sshd` روی Raspberry Pi؛ درخواست‌ها را دریافت و احراز هویت را انجام می‌دهد.
- **SSH Session (نشست):** ارتباط برقرارشده‌ای که از طریق آن فرمان‌های ترمینال را روی دستگاه مقصد اجرا می‌کنیم.

**نکته کلیدی:** ممکن است از ویندوز وصل شویم، اما پس از ورود، دستورها روی **لینوکسِ Raspberry Pi** اجرا می‌شوند. بنابراین دستورهای سمت Raspberry Pi در ویندوز، مک و لینوکس **یکسان** هستند.

### ۱.۳. قرارداد برچسب‌گذاری دستورها در این راهنما

هر جا نوشته‌ایم:

- **[macOS / Linux — کامپیوتر شخصی]**: فرمان را در Terminal مک یا لینوکس خودتان اجرا کنید.
- **[Windows — PowerShell کامپیوتر شخصی]**: فرمان را در PowerShell ویندوز اجرا کنید.
- **[همه سیستم‌عامل‌ها — کامپیوتر شخصی]**: فرمان `ssh` از Terminal مک/لینوکس یا PowerShell ویندوز قابل اجراست.
- **[Raspberry Pi — بعد از اتصال SSH]**: فرمان روی Raspberry Pi اجرا می‌شود، حتی اگر کامپیوتر شما ویندوز باشد.

نمونه خط فرمان مک:

```text
(base) ➜  ~
```

نمونه خط فرمان ویندوز:

```text
PS C:\Users\YourName>
```

نمونه خط فرمان Raspberry Pi بعد از ورود:

```text
iotuser@iot-pi:~ $
```

`$` یا `>` آخر خط، بخشی از دستوری که باید تایپ شود **نیست**.

### ۱.۴. مقادیر نمونه — قبل از کپی‌کردن حتماً بررسی کنید

| مفهوم | مقدار آموزشی | آیا باید تغییر کند؟ |
|---|---|---|
| مدل دستگاه | `Raspberry Pi 4 Model B` | در صورت استفاده از مدل دیگر، بله |
| نام دستگاه (Hostname) | `iot-pi` | دلخواه |
| نام کاربری دستگاه | `iotuser` | اگر در Imager نام دیگری گذاشته‌اید، بله |
| نام شبکه محلی (mDNS) | `iot-pi.local` | تابع hostname و کارکرد mDNS |
| IP نمونه | `192.168.1.50` | **حتماً IP واقعی شبکه خودتان** |
| Gateway نمونه | `192.168.1.1` | **حتماً از شبکه واقعی** |
| شبکه نمونه | `192.168.1.0/24` | **حتماً از شبکه واقعی** |
| پورت SSH پیش‌فرض | `22/tcp` | معمولاً ثابت، مگر خودتان تغییر دهید |

> **هشدار:** IPهای این README، به‌جز زمانی که خروجی یک دستور را توضیح می‌دهیم، فقط مثال هستند. کپی‌کردن IP، Gateway یا محدوده شبکه فرضی ممکن است ارتباط Raspberry Pi را قطع کند.

## ۲. پیش‌نیازها و ابزارهای مورد نیاز

### سخت‌افزار

1. Raspberry Pi 4 Model B (در این پروژه مدل 4GB، اما مراحل برای بسیاری از مدل‌های دیگر نیز مشابه است).
2. منبع تغذیه مناسب و پایدار برای مدل Raspberry Pi.
3. کارت microSD سازگار و کارت‌خوان متصل به کامپیوتر.
4. یک کامپیوتر با macOS، Linux یا Windows 10/11.
5. شبکه محلی Wi-Fi یا کابل Ethernet و یک روتر/Access Point.

### نرم‌افزار

- [Raspberry Pi Imager](https://www.raspberrypi.com/software/)، قابل دریافت برای macOS، Windows و Linux.
- یک Terminal در مک/لینوکس، یا PowerShell در ویندوز.
- SSH Client؛ در macOS و اغلب توزیع‌های Linux آماده است. در Windows 10/11 نیز معمولاً OpenSSH Client نصب شده است.

**[macOS / Linux — کامپیوتر شخصی]** بررسی وجود SSH Client و ابزار ساخت کلید:

```bash
ssh -V
command -v ssh-keygen
```

**[Windows — PowerShell کامپیوتر شخصی]**:

```powershell
ssh -V
Get-Command ssh
Get-Command ssh-keygen
```

اگر فرمان `ssh` در ویندوز شناسایی نشد، از **Settings → Optional features** نصب **OpenSSH Client** را بررسی کنید؛ این کار **نصب SSH Server روی ویندوز** نیست. در توزیع Debian/Ubuntu می‌توان بسته کلاینت را در صورت نیاز با `sudo apt install openssh-client` نصب کرد.

> **هشدار پاک‌شدن اطلاعات:** Raspberry Pi Imager محتوای حافظه‌ای را که برای نوشتن سیستم‌عامل انتخاب می‌کنید پاک می‌کند. مدل و ظرفیت کارت را دو بار بررسی کنید.

## ۳. نصب Raspberry Pi OS با Raspberry Pi Imager

این مرحله **با رابط گرافیکی** انجام می‌شود و در هر سه سیستم‌عامل تقریباً مشابه است.

### ۳.۱. نصب و اجرای Imager

1. از [صفحه رسمی Imager](https://www.raspberrypi.com/software/) نسخه مخصوص **macOS، Windows یا Linux** را دریافت و نصب کنید.
2. کارت microSD را به کامپیوتر وصل کنید.
3. Raspberry Pi Imager را اجرا کنید.
4. در قسمت **Device**، مدل `Raspberry Pi 4` را انتخاب کنید.
5. در **OS**، گزینه `Raspberry Pi OS Lite (64-bit)` را انتخاب کنید.
6. در **Storage**، کارت microSD صحیح را انتخاب کنید.
7. وارد بخش **OS Customisation** شوید. عنوان دقیق دکمه‌ها و ترتیب صفحه‌ها بین نسخه‌های Imager ممکن است متفاوت باشد.

**چرا OS Lite؟** چون دستگاه را بدون دسکتاپ گرافیکی راه‌اندازی می‌کنیم و محیط خط فرمان برای پروژه SSH و مراحل اولیه IoT کافی است. نسخه Lite عموماً منابع کمتری نسبت به نسخه Desktop مصرف می‌کند.

### ۳.۲. تنظیمات اولیه سیستم‌عامل

| تنظیم Imager | مقدار آموزشی | دلیل |
|---|---|---|
| `Hostname` | `iot-pi` | نام Raspberry Pi در شبکه |
| `Username` | `iotuser` | حساب کاربری معمول برای ورود؛ نام `pi` را پیش‌فرض فرض نکنید |
| `Password` | یک رمز قوی و یکتا | برای ورود اولیه و بعضی عملیات حساب کاربری |
| `Wi-Fi / Wireless LAN` | نام و رمز Wi-Fi واقعی | برای اتصال شبکه بی‌سیم |
| `Locale / Time zone / Keyboard` | مطابق محل استفاده | تنظیم زمان، منطقه و صفحه‌کلید |
| `Remote Access` | `Enable SSH` | فعال‌کردن سرویس SSH برای حالت Headless |

**SSID** نام شبکه Wi-Fi است؛ Password Wi-Fi با Password کاربر `iotuser` تفاوت دارد.

اگر به‌جای Wi-Fi از کابل Ethernet استفاده می‌کنید، کابل شبکه را به پورت دستگاه و شبکه مناسب وصل کنید؛ معمولاً DHCP روتر تنظیمات IP را به Pi می‌دهد.

### ۳.۳. انتخاب روش احراز هویت SSH در Imager

Imager معمولاً یکی از این دو شیوه را ارائه می‌کند:

**مسیر A — مناسب شروع آموزش:**

- `Use password authentication` را انتخاب کنید.
- بعد از اولین ورود به Raspberry Pi، در [بخش ۷](#s7) کلید SSH بسازید و منتقل کنید.
- پس از **تأیید عملی اتصال با کلید**، می‌توانید ورود با رمز عبور را اختیاری غیرفعال کنید.

**مسیر B — استفاده از کلید عمومی از همان اولین بوت:**

- **قبل از فشردن Write** روی کامپیوتر خود کلید SSH بسازید؛ دستورهای مخصوص macOS/Linux/Windows در [بخش ۷.۳](#s73) آمده است.
- `Use public key authentication` را انتخاب کنید.
- **فقط فایل عمومی** (`id_ed25519.pub`) را در Imager انتخاب یا محتوایش را وارد کنید؛ هرگز فایل بدون `.pub` را به Imager، GitHub یا دستگاه مقصد ندهید.
- در این مسیر ممکن است ورود با رمز عبور SSH از ابتدا قابل استفاده نباشد؛ اولین اتصال را با کلید آزمایش کنید و بخش انتقال کلید را تکرار نکنید.

> انتخاب روش در Imager ممکن است در نسخه‌های مختلف رابط متفاوتی داشته باشد؛ هنگام استفاده، متن فعلی برنامه را بررسی کنید.

### ۳.۴. نوشتن سیستم‌عامل

1. تنظیمات و کارت انتخاب‌شده را مرور کنید.
2. گزینه **Write** را بزنید.
3. منتظر پایان نوشتن و مرحله Verify بمانید.
4. کارت microSD را به شکل امن Eject/Unmount کنید.

**نتیجه مورد انتظار:** کارت microSD آماده بوت Raspberry Pi است و تنظیمات اولیه کاربر/شبکه/SSH همراه آن ثبت شده‌اند.

## ۴. اولین بوت و اتصال به شبکه

1. کارت microSD آماده‌شده را داخل Raspberry Pi قرار دهید.
2. اگر Ethernet استفاده می‌کنید، کابل را وصل کنید.
3. منبع تغذیه مناسب را به Raspberry Pi متصل کنید.
4. برای تکمیل بوت اولیه و اتصال به شبکه کمی فرصت بدهید؛ زمان دقیق به سیستم و کارت حافظه بستگی دارد.
5. کامپیوتر شخصی را به شبکه‌ای وصل کنید که امکان ارتباط با Raspberry Pi را دارد.

**چرا «یک شبکه» مهم است؟** برای SSH محلی باید کامپیوتر به IP دستگاه مقصد مسیر ارتباطی داشته باشد. اتصال دو دستگاه به Wi-Fi هم‌نام همیشه کافی نیست: برخی شبکه‌های Guest یا تنظیمات **Client Isolation** ارتباط دستگاه‌ها با یکدیگر را محدود می‌کنند.

اگر Pi و کامپیوتر روی دو VLAN یا زیرشبکه متفاوت هستند، ممکن است حتی با IP صحیح نیاز به مسیریابی و مجوز فایروال داشته باشید. این README حالت ساده شبکه محلی را آموزش می‌دهد.

## ۵. پیدا کردن آدرس Raspberry Pi در شبکه

### ۵.۱. تفاوت Hostname، IP، DNS و mDNS

- **Hostname** نام منطقی دستگاه است؛ اینجا `iot-pi`.
- **IP Address** آدرسی است که در شبکه برای رساندن بسته‌ها استفاده می‌شود؛ مثلاً `192.168.1.50`.
- **DNS** نام را به آدرس تبدیل می‌کند؛ در شبکه محلی ممکن است روتر این کار را انجام دهد.
- **mDNS** به دستگاه‌های شبکه محلی امکان می‌دهد نام‌هایی مثل `iot-pi.local` را بدون DNS معمولی پیدا کنند؛ به پشتیبانی سیستم‌عامل و شبکه نیاز دارد.
- **DHCP** معمولاً به‌طور خودکار IP، Gateway و DNS را از روتر دریافت می‌کند.

`iot-pi.local` آدرس اینترنتی عمومی نیست؛ برای شناسایی یک دستگاه در شبکه محلی استفاده می‌شود.

### ۵.۲. امتحان نام `iot-pi.local`

**[macOS / Linux — کامپیوتر شخصی]**:

```bash
ping -c 3 iot-pi.local
```

**[Windows — PowerShell کامپیوتر شخصی]**:

```powershell
ping -n 3 iot-pi.local
```

گزینه `-c 3` در macOS/Linux و `-n 3` در Windows درخواست می‌کند **سه** بسته آزمایشی ارسال شود.

اگر پاسخ دریافت کردید، شبکه یا نام‌حل‌کنی در سطحی کار می‌کند. **بااین‌حال، Ping موفق به معنای بازبودن SSH نیست**؛ و Ping ناموفق لزوماً به معنای خاموش‌بودن Pi نیست، چون ممکن است ICMP مسدود باشد یا mDNS درست کار نکند.

**[Linux — کامپیوتر شخصی، روش کمکی]**:

```bash
getent hosts iot-pi.local
```

این دستور فقط در توزیع‌هایی مفید است که نام‌حل‌کنی mDNS به‌درستی پیکربندی شده باشد؛ ممکن است برای آن Avahi یا `libnss-mdns` لازم باشد.

**[Windows — PowerShell کامپیوتر شخصی، بررسی پورت SSH]**:

```powershell
Test-NetConnection iot-pi.local -Port 22
```

این دستور تلاش می‌کند اتصال TCP به پورت SSH را بررسی کند؛ در خروجی، `TcpTestSucceeded : True` نشانه قابل‌دسترس‌بودن آن پورت است. اگر نام `.local` در ویندوز حل نشد، IP واقعی را به‌جای آن بگذارید.

### ۵.۳. اگر نام پیدا نشد، از روتر کمک بگیرید

با مرورگر هر سه سیستم‌عامل می‌توان وارد پنل روتر شد. در بخش‌هایی با نام‌هایی مثل `Connected Devices`، `DHCP Clients` یا `LAN`، دستگاه `iot-pi` و IP مربوط به آن را پیدا کنید.

مثلاً ممکن است روتر نمایش دهد:

```text
Hostname:  iot-pi
IPv4:      192.168.1.50       <-- مثال، نه IP قطعی دستگاه شما
```

آدرس را یادداشت کنید. اگر روش mDNS کار نکرد، ادامه آموزش را با **IP واقعی** انجام دهید.

### ۵.۴. چرا گاهی دو IP مشاهده می‌کنیم؟

اگر قبلاً وارد Raspberry Pi شده‌اید، **[Raspberry Pi — بعد از اتصال SSH]** اجرا کنید:

```bash
hostname -I
ip -br addr
```

خروجی ممکن است شبیه زیر باشد:

```text
192.168.1.10 192.168.1.9

lo     UNKNOWN   127.0.0.1/8 ...
eth0   UP        192.168.1.10/24 ...
wlan0  UP        192.168.1.9/24 ...
```

در این **مثال**، Pi هم با Ethernet (`eth0`) و هم Wi-Fi (`wlan0`) متصل است و برای هر رابط یک IP گرفته است؛ اما صرف دیدن دو IP **به‌تنهایی اثبات نمی‌کند** دقیقاً به این دو رابط تعلق دارند. برای تشخیص قطعی از `ip -br addr` استفاده می‌کنیم.

**نکته IPv6:** ممکن است هنگام `ssh iotuser@iot-pi.local` اتصال با آدرسی مثل `fe80::...%en0` برقرار شود. `fe80::` آدرس IPv6 نوع Link-local است و `%en0` رابط شبکه را در مک مشخص می‌کند. وجود آن طبیعی است. اگر بعداً UFW را فقط برای IPv4 مجاز کردید، باید SSH را نیز با IPv4 آزمایش کنید؛ [بخش ۱۱](#s11) را ببینید.

## ۶. اولین اتصال SSH و بررسی هویت سرور

### ۶.۱. معنی دستور اتصال

**[همه سیستم‌عامل‌ها — کامپیوتر شخصی]**؛ در Terminal مک/لینوکس یا PowerShell ویندوز:

```bash
ssh iotuser@iot-pi.local
```

اگر `.local` پاسخ نداد، از **IP واقعی** استفاده کنید (این IP صرفاً نمونه است):

```bash
ssh iotuser@192.168.1.50
```

اجزای فرمان:

| جزء | معنی |
|---|---|
| `ssh` | برنامه کلاینت ارتباط امن |
| `iotuser` | نام کاربری **روی Raspberry Pi**، نه روی لپ‌تاپ شما |
| `@` | جداکننده کاربر و مقصد |
| `iot-pi.local` یا IP | دستگاه مقصد |

در حالت معمول، SSH از TCP port `22` استفاده می‌کند و محتوای ارتباط را رمزگذاری می‌کند.

### ۶.۲. هشدار اولین اتصال: Host Key چیست؟

ممکن است ببینید:

```text
The authenticity of host 'iot-pi.local (...)' can't be established.
ED25519 key fingerprint is SHA256:...
Are you sure you want to continue connecting (yes/no/[fingerprint])?
```

این اثرانگشت مربوط به **کلید میزبانِ سرور Raspberry Pi** است؛ با کلید شخصی خودتان که بعداً در بخش ۷ می‌سازید فرق دارد.

**منطق امنیتی:** مک/ویندوز/لینوکس باید بررسی کند دستگاهی که جواب داده همان Pi موردنظر است، نه یک دستگاه جعلی. برای تأیید مطمئن، اثرانگشت را با مقداری که از خود Pi از مسیر مورداعتماد (مثلاً نمایشگر و کیبورد محلی یا کانال مدیریتی معتبر) گرفته‌اید مقایسه کنید.

**[Raspberry Pi — با دسترسی محلی مورداعتماد]** نمایش اثرانگشت کلید میزبان Ed25519:

```bash
ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
```

اگر اثرانگشت درست بود، در سؤال اولیه `yes` را وارد کنید. کلاینت اطلاعات هویت میزبان را در فایل `known_hosts` ثبت می‌کند تا در اتصال‌های بعدی تغییر غیرمنتظره تشخیص داده شود.

**هشدار:** هرگز پیام `REMOTE HOST IDENTIFICATION HAS CHANGED` را صرفاً با پاک‌کردن `known_hosts` نادیده نگیرید؛ ابتدا دلیل تغییر کلید میزبان یا جایگزین‌شدن دستگاه را بررسی کنید.

### ۶.۳. واردکردن Password (در مسیر آموزشی A)

اگر روش Password Authentication را در Imager فعال کرده باشید، پیامی مشابه زیر می‌بینید:

```text
iotuser@iot-pi.local's password:
```

رمز حساب **`iotuser` روی Raspberry Pi** را وارد کنید. هنگام تایپ Password معمولاً هیچ کاراکتر یا ستاره‌ای روی صفحه نمایش داده نمی‌شود؛ این رفتار عمدی و طبیعی است.

اگر در Imager احراز هویت فقط با کلید عمومی انتخاب کرده‌اید، این مرحله ممکن است وجود نداشته باشد؛ باید با کلید خصوصی متناظر وارد شوید.

### ۶.۴. چگونه بفهمیم واقعاً وارد Raspberry Pi شده‌ایم؟

وقتی اتصال برقرار شد، خط فرمان شبیه زیر است:

```text
iotuser@iot-pi:~ $
```

از این لحظه **فرمان‌ها روی Pi اجرا می‌شوند**، نه روی کامپیوتر شخصی.

**[Raspberry Pi — بعد از اتصال SSH]**:

```bash
whoami
hostname
hostname -I
ip -br addr
ip route
```

| دستور | چرا اجرا می‌شود؟ |
|---|---|
| `whoami` | نمایش حساب کاربری فعلی؛ انتظار `iotuser` در مثال |
| `hostname` | نمایش نام دستگاه؛ انتظار `iot-pi` در مثال |
| `hostname -I` | نمایش IPهای منتسب به دستگاه؛ ممکن است چند آدرس نشان دهد |
| `ip -br addr` | نمایش خلاصه رابط‌های شبکه، وضعیت و IP هرکدام |
| `ip route` | نمایش مسیرهای شبکه و Gateway؛ مثلاً مسیر پیش‌فرض `default via ...` |

برای پایان‌دادن به نشست SSH و بازگشت به ترمینال دستگاه شخصی:

```bash
exit
```

`exit` فقط نشست ترمینال SSH را می‌بندد؛ Raspberry Pi را خاموش نمی‌کند.

## ۷. ساخت، انتقال و آزمایش SSH Key

### ۷.۱. اصلاً چرا SSH Key؟

روش ساده ورود، دانستن Password حساب Raspberry Pi است. در روش SSH Key، کلاینت به‌جای ارسال رمز حساب، با **امضای دیجیتال** ثابت می‌کند کلید خصوصی متناظر با یکی از کلیدهای عمومی مجاز را دارد.

```text
کامپیوتر شخصی                          Raspberry Pi
-----------------                      ----------------------------
~/.ssh/id_ed25519                       /home/iotuser/.ssh/authorized_keys
    PRIVATE KEY                             PUBLIC KEY
    محرمانه می‌ماند                         برای تأیید امضا استفاده می‌شود
         |                                         ^
         +--- اثبات مالکیت با امضای دیجیتال -------+

                  کلید خصوصی ارسال نمی‌شود.
```

دو فایل اصلی کلید کاربر:

| فایل | کاربرد | قابل انتقال به Pi؟ |
|---|---|---|
| `id_ed25519` | **Private Key**؛ کلید محرمانه روی دستگاه شما | **خیر** |
| `id_ed25519.pub` | **Public Key**؛ کلید عمومی متناظر | **بله** |

**تفاوت با Host Key:** کلید میزبان در بخش ۶ برای شناسایی *خود Raspberry Pi* بود؛ اینجا کلید کاربر برای شناسایی *کسی که می‌خواهد وارد Raspberry Pi شود* است.

### ۷.۲. قدم صفر: بررسی کلید موجود، بدون بازنویسی

ابتدا مطمئن شوید در **کامپیوتر شخصی** هستید (اگر خط فرمان `iotuser@iot-pi` می‌بینید، با `exit` خارج شوید).

**[macOS / Linux — کامپیوتر شخصی]**:

```bash
ls -l ~/.ssh/id_ed25519 ~/.ssh/id_ed25519.pub
```

**[Windows — PowerShell کامپیوتر شخصی]**:

```powershell
Test-Path "$env:USERPROFILE\.ssh\id_ed25519"
Test-Path "$env:USERPROFILE\.ssh\id_ed25519.pub"
```

در PowerShell مقدار `True` یعنی فایل وجود دارد و `False` یعنی در آن مسیر وجود ندارد.

- اگر **هر دو فایل** وجود دارند، می‌توانید از همان جفت‌کلید استفاده کنید (اگر به آن دسترسی و اعتماد دارید) و مرحله تولید را رد کنید.
- اگر **هر دو فایل** وجود ندارند، مرحله بعد را انجام دهید.
- اگر **فقط یکی** وجود دارد، بدون بررسی کلید جدید را روی همان مسیر نسازید؛ ممکن است به کلیدهای قبلی آسیب بزنید. یک نام جدید برای جفت‌کلید انتخاب کنید یا وضعیت را جداگانه بررسی کنید.

<a id="s73"></a>

### ۷.۳. ساخت جفت کلید روی کامپیوتر شخصی

**[macOS / Linux — کامپیوتر شخصی]**:

```bash
ssh-keygen -t ed25519 -C "laptop-to-iot-pi"
```

**[Windows — PowerShell کامپیوتر شخصی]**:

```powershell
ssh-keygen -t ed25519 -C "laptop-to-iot-pi"
```

این فرمان روی هر سه سیستم‌عامل **یکسان** است، چون از برنامه OpenSSH استفاده می‌کنیم. تفاوت اصلی در مسیر فایل و محیط Terminal است.

| بخش | توضیح |
|---|---|
| `ssh-keygen` | ابزار ساخت و مدیریت کلیدهای SSH |
| `-t ed25519` | انتخاب الگوریتم Ed25519 برای جفت‌کلید امضای دیجیتال |
| `-C "laptop-to-iot-pi"` | توضیح دلخواه جهت شناسایی کلید؛ نه Password است و نه نام کاربری |

ابتدا پرسیده می‌شود:

```text
Enter file in which to save the key (.../.ssh/id_ed25519):
```

اگر مسیر پیش‌فرض قبلاً **خالی** بوده است، Enter بزنید. مسیر پیش‌فرض روی macOS/Linux معمولاً `~/.ssh/id_ed25519` و در Windows معمولاً `C:\Users\YourName\.ssh\id_ed25519` است.

سپس:

```text
Enter passphrase (empty for no passphrase):
Enter same passphrase again:
```

**Passphrase با Password Raspberry Pi متفاوت است:**

- Password حساب `iotuser` برای ورود به خود Raspberry Pi است.
- Passphrase برای **محافظت از فایل کلید خصوصی** روی کامپیوتر شخصی استفاده می‌شود؛ داشتن Passphrase قوی توصیه می‌شود.
- ممکن است هنگام استفاده از کلید، Passphrase پرسیده شود، حتی وقتی Password حساب Raspberry Pi دیگر پرسیده نمی‌شود.

**اگر عمداً کلید را در فایل دیگری ساختید، تمام دستورهای مراحل بعد را با همان مسیر جدید اجرا کنید.**

### ۷.۴. بررسی ساخته‌شدن و مشاهده Public Key

**[macOS / Linux — کامپیوتر شخصی]**:

```bash
ls -l ~/.ssh/id_ed25519 ~/.ssh/id_ed25519.pub
cat ~/.ssh/id_ed25519.pub
```

**[Windows — PowerShell کامپیوتر شخصی]**:

```powershell
Get-Item "$env:USERPROFILE\.ssh\id_ed25519", "$env:USERPROFILE\.ssh\id_ed25519.pub"
Get-Content "$env:USERPROFILE\.ssh\id_ed25519.pub"
```

شکل تقریبی محتوای Public Key:

```text
ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAA... laptop-to-iot-pi
```

قسمت وسط **کلید عمومی کدگذاری‌شده به شکل متن** است؛ `laptop-to-iot-pi` صرفاً توضیح آن است. سه نقطه در نمونه بالا نمایشی‌اند، نه محتوای یک کلید واقعی.

**کلید خصوصی را چاپ، منتشر، ایمیل یا در Repository آپلود نکنید.** حتی اگر Repository خصوصی باشد، بهتر است چنین فایلی اصلاً وارد Git نشود.

### ۷.۵. Raspberry Pi کلید عمومی را کجا نگه می‌دارد؟

روی Raspberry Pi، فایل زیر برای کاربر مثال ما استفاده می‌شود:

```text
/home/iotuser/.ssh/authorized_keys
```

این فایل می‌تواند **چند کلید عمومی** داشته باشد (هر کلید یک خط). نام آن به معنی «کلیدهایی که اجازه ورود دارند» است.

دو نکته مهم:

1. انتقال کلید عمومی معمولاً یک بار برای هر کلید انجام می‌شود.
2. **نباید فایل `authorized_keys` را با کلید جدید جایگزین کنید**، چون ممکن است کلیدهای مجاز قبلی را از بین ببرید؛ باید به آن اضافه کنید.

### ۷.۶. انتقال Public Key به Raspberry Pi

این مرحله برای مسیر آموزشی **Password Authentication اولیه** است. اگر کلید را از قبل در Imager ثبت کرده‌اید و ورود با کلید کار می‌کند، از این مرحله عبور کنید.

#### روش macOS و Linux: `ssh-copy-id` (اگر نصب است)

**[macOS / Linux — کامپیوتر شخصی]**:

```bash
ssh-copy-id -i ~/.ssh/id_ed25519.pub iotuser@iot-pi.local
```

`ssh-copy-id` ابزار کمکی انتقال کلید عمومی به `authorized_keys` است و معمولاً با واردکردن یک‌باره Password حساب مقصد کار می‌کند. **در همه نصب‌های macOS یا Linux به‌صورت پیش‌فرض وجود ندارد**؛ اگر `command not found` گرفتید، از روش بعدی استفاده کنید.

#### روش عمومی macOS و Linux: انتقال با ورودی استاندارد SSH

**[macOS / Linux — کامپیوتر شخصی]**:

```bash
ssh iotuser@iot-pi.local 'umask 077; mkdir -p ~/.ssh; cat >> ~/.ssh/authorized_keys; chmod 700 ~/.ssh; chmod 600 ~/.ssh/authorized_keys' < ~/.ssh/id_ed25519.pub
```

#### روش Windows PowerShell: انتقال با Pipeline

**[Windows — PowerShell کامپیوتر شخصی]**:

```powershell
Get-Content -Raw "$env:USERPROFILE\.ssh\id_ed25519.pub" | ssh iotuser@iot-pi.local "umask 077; mkdir -p ~/.ssh; cat >> ~/.ssh/authorized_keys; chmod 700 ~/.ssh; chmod 600 ~/.ssh/authorized_keys"
```

روش ویندوز همان **داده عمومی** را به ورودی SSH می‌فرستد؛ فقط نحو خواندن فایل در PowerShell متفاوت است. این فرمان را در **PowerShell** اجرا کنید، نه CMD.

> اگر `.local` قابل شناسایی نیست، در هر کدام از فرمان‌های بالا `iot-pi.local` را با IP **واقعی** Pi جایگزین کنید. هر بار اجرای دستی فرمان انتقال با `cat >>` ممکن است همان کلید را دوباره اضافه کند؛ معمولاً مانع ورود نیست، اما تکرار بی‌دلیل نکنید.

#### فرمان انتقال دقیقاً چه می‌کند؟

| جزء | توضیح |
|---|---|
| `ssh iotuser@iot-pi.local '...'` | به Raspberry Pi وصل می‌شود و دستورهای داخل کوتیشن را **روی Pi** اجرا می‌کند |
| `umask 077` | مجوزهای پیش‌فرض ایجاد فایل/پوشه را محدود می‌کند |
| `mkdir -p ~/.ssh` | پوشه SSH حساب `iotuser` را در صورت نیاز می‌سازد؛ `-p` از خطای «وجود دارد» جلوگیری می‌کند |
| `cat >> ~/.ssh/authorized_keys` | متن کلید عمومیِ دریافت‌شده از ورودی را **به انتهای** فایل مجازها اضافه می‌کند |
| `chmod 700 ~/.ssh` | مجوز پوشه را به مالک محدود می‌کند |
| `chmod 600 ~/.ssh/authorized_keys` | خواندن و نوشتن فایل را به مالک محدود می‌کند |
| `< ~/.ssh/id_ed25519.pub` | در macOS/Linux فایل عمومی را به ورودی `ssh` می‌دهد؛ روی **کامپیوتر شخصی** تفسیر می‌شود |
| `Get-Content -Raw ... \| ssh ...` | معادل انتقال ورودی در PowerShell ویندوز |

**چرا `>>` مهم است؟** علامت `>` معمولاً محتوای قبلی فایل مقصد را جایگزین می‌کند؛ `>>` محتوا را اضافه می‌کند. اگر از قبل چند کلید مجاز دارید، جایگزین‌کردن فایل می‌تواند دسترسی دستگاه‌های دیگر را قطع کند.

**چرا مجوزها مهم‌اند؟** OpenSSH با تنظیم معمول `StrictModes` ممکن است به‌دلیل مجوزهای ناامن مسیر و فایل‌ها، کلید را نپذیرد.

#### بررسی فایل روی Pi (اختیاری)

**[Raspberry Pi — بعد از اتصال SSH]**:

```bash
ls -ld ~/.ssh
ls -l ~/.ssh/authorized_keys
```

در حالت معمول مجوز پوشه شبیه `drwx------` و فایل شبیه `-rw-------` خواهد بود. **لازم نیست خود کلید خصوصی را روی Pi داشته باشید؛ آنجا فقط Public Key قرار می‌گیرد.**

### ۷.۷. آزمایش اتصال واقعاً «فقط با کلید»

**[macOS / Linux — کامپیوتر شخصی]**:

```bash
ssh -i ~/.ssh/id_ed25519 -o IdentitiesOnly=yes -o PreferredAuthentications=publickey -o PasswordAuthentication=no -o KbdInteractiveAuthentication=no iotuser@iot-pi.local
```

**[Windows — PowerShell کامپیوتر شخصی]**:

```powershell
ssh -i "$env:USERPROFILE\.ssh\id_ed25519" -o IdentitiesOnly=yes -o PreferredAuthentications=publickey -o PasswordAuthentication=no -o KbdInteractiveAuthentication=no iotuser@iot-pi.local
```

| گزینه | کارکرد |
|---|---|
| `-i` | مسیر Private Key انتخابی روی **کامپیوتر شخصی** |
| `IdentitiesOnly=yes` | از ارائه کلیدهای اضافی عامل SSH جلوگیری می‌کند؛ با `-i` کلید مشخص را آزمایش می‌کنیم |
| `PreferredAuthentications=publickey` | اولویت دادن به روش کلید عمومی |
| `PasswordAuthentication=no` | جلوگیری از ورود با روش Password Authentication در **این آزمایش** |
| `KbdInteractiveAuthentication=no` | جلوگیری از fallback به احراز هویت تعاملی در **این آزمایش** |

**نتیجه موفق:** خط فرمان `iotuser@iot-pi:~ $` ظاهر می‌شود. ممکن است **Passphrase کلید خصوصی** پرسیده شود؛ این به معنی درخواست Password حساب Raspberry Pi نیست.

**نتیجه ناموفق:** پیام‌هایی مانند `Permission denied (publickey)` ظاهر می‌شوند. در این صورت هنوز تنظیمات ورود با Password را تغییر ندهید؛ به [بخش عیب‌یابی](#s13) بروید.

برای عیب‌یابی از خروجی جزئیات اتصال کمک بگیرید:

**[macOS / Linux — کامپیوتر شخصی]**:

```bash
ssh -v -i ~/.ssh/id_ed25519 -o IdentitiesOnly=yes iotuser@iot-pi.local
```

**[Windows — PowerShell کامپیوتر شخصی]**:

```powershell
ssh -v -i "$env:USERPROFILE\.ssh\id_ed25519" -o IdentitiesOnly=yes iotuser@iot-pi.local
```

مثلاً پیام `Authenticated ... using "publickey"` نشان می‌دهد احراز هویت کلید عمومی موفق بوده است. با `-v` اطلاعات تشخیصی بیشتری می‌بینید؛ قبل از انتشار لاگ، اطلاعات شخصی یا آدرس‌های شبکه را بررسی کنید.

### ۷.۸. تفاوت سه فایل پرکاربرد SSH

| فایل | معمولاً کجاست؟ | هدف |
|---|---|---|
| `id_ed25519` | کامپیوتر شخصی | **کلید خصوصی کاربر**؛ محرمانه |
| `authorized_keys` | Raspberry Pi | **کلیدهای عمومی مجاز کاربران** برای ورود به این حساب |
| `known_hosts` | کامپیوتر شخصی | **کلیدهای میزبان سرورها** برای شناسایی Pi و دیگر سرورها |

پس `known_hosts` و `authorized_keys` یک کار انجام نمی‌دهند: اولی کمک می‌کند **کلاینت سرور را بشناسد**، دومی کمک می‌کند **سرور ورود کاربر را تأیید کند**.

## ۸. غیرفعال‌کردن ورود با رمز عبور (اختیاری)

> **قانون طلایی:** این بخش را **فقط** زمانی انجام دهید که ورود با SSH Key طبق بخش ۷.۷ از یک پنجره تازه با موفقیت آزمایش شده است. **نشست SSH قدیمی را باز نگه دارید** تا در صورت بروز مشکل بتوانید تنظیمات را برگردانید.

### ۸.۱. چرا این کار را انجام می‌دهیم؟

اگر سرور هم Password و هم Public Key را بپذیرد، مهاجمی که رمز عبور حساب را به دست بیاورد ممکن است همچنان بتواند از راه SSH وارد شود. غیرفعال‌کردن Password Authentication، این روش ورود را از SSH حذف می‌کند.

این موضوع با حذف Password حساب لینوکس متفاوت است؛ حساب `iotuser` همچنان وجود دارد و ممکن است برای `sudo` یا ورود از کنسول محلی از Password استفاده شود.

### ۸.۲. دو پنجره باز کنید

- **پنجره شماره ۱:** نشست باز `iotuser@iot-pi:~ $` روی Raspberry Pi؛ **نبندید**.
- **پنجره شماره ۲:** ترمینال یا PowerShell کامپیوتر شخصی برای آزمایش اتصال جدید.

این کار یک روش بازیابی ساده است: حتی اگر **اتصال جدید** مسدود شود، ممکن است نشست اول هنوز فعال باشد و بتوانید اشتباه را اصلاح کنید. البته نشست اول تضمینی برای بازیابی در تمام خطاها نیست؛ دسترسی فیزیکی به Pi همیشه مطمئن‌تر است.

### ۸.۳. مشاهده تنظیمات فعلی روی Raspberry Pi

**[Raspberry Pi — پنجره شماره ۱]**:

```bash
sudo sshd -T | grep -E '^(pubkeyauthentication|passwordauthentication|kbdinteractiveauthentication|permitrootlogin) '
```

توضیح دستور:

- `sudo`: اجرای دستور با دسترسی مدیریتی.
- `sshd`: برنامه سرور OpenSSH.
- `-T`: نمایش تنظیمات مؤثر فعلی با توجه به فایل‌های پیکربندی (در حالت معمول).
- `|`: انتقال خروجی دستور اول به دستور دوم.
- `grep -E`: انتخاب فقط خطوطی که با الگوی موردنظر مطابقت دارند.

برای نمونه **ممکن است** پیش از تغییر چنین خروجی‌ای ببینید:

```text
pubkeyauthentication yes
passwordauthentication yes
kbdinteractiveauthentication no
permitrootlogin prohibit-password
```

این فقط خروجی نمونه است؛ مقدارهای واقعی سیستم را بخوانید.

### ۸.۴. ساخت فایل تنظیمات مستقل

**[Raspberry Pi — پنجره شماره ۱]** ابتدا فایل‌های فعلی را ببینید:

```bash
sudo ls -l /etc/ssh/sshd_config.d/
```

اگر فایلی به نام `01-iot-course.conf` از قبل وجود داشت، آن را بدون بررسی **بازنویسی نکنید**. در نصب معمولی که چنین فایلی وجود ندارد، آن را بسازید:

```bash
sudo nano /etc/ssh/sshd_config.d/01-iot-course.conf
```

متن زیر را در ویرایشگر قرار دهید:

```sshconfig
PubkeyAuthentication yes
PasswordAuthentication no
KbdInteractiveAuthentication no
PermitRootLogin no
```

در `nano` برای ذخیره `Ctrl + O`، سپس Enter و برای خروج `Ctrl + X` را بزنید. این ترکیب‌ها در **ترمینال متصل به Pi** عمل می‌کنند، فرقی ندارد از Windows، Linux یا macOS متصل شده باشید.

**معنای تنظیم‌ها:**

| تنظیم | عملکرد |
|---|---|
| `PubkeyAuthentication yes` | امکان احراز هویت با کلید عمومی را فعال نگه می‌دارد |
| `PasswordAuthentication no` | ورود SSH با روش رمز عبور را غیرفعال می‌کند |
| `KbdInteractiveAuthentication no` | احراز هویت تعاملی (که گاهی می‌تواند رمز بخواهد) را غیرفعال می‌کند |
| `PermitRootLogin no` | ورود **مستقیم** حساب `root` از طریق SSH را ممنوع می‌کند؛ `sudo` برای کاربر مجاز همچنان می‌تواند کار کند |

**چرا نام فایل با `01-` شروع شده؟** در پیکربندی‌های معمول Debian/Raspberry Pi OS، `Include /etc/ssh/sshd_config.d/*.conf` فایل‌ها را به ترتیب نام می‌خواند و OpenSSH برای اغلب گزینه‌ها اولین مقدار خوانده‌شده را به کار می‌برد. بنابراین فایل `99-...` ممکن است به‌خاطر فایل زودتر **بی‌اثر** شود. بااین‌حال، نام فایل به‌تنهایی تضمین نیست؛ نتیجه واقعی را با `sshd -T` بررسی می‌کنیم. اگر پیکربندی شما `Match` یا Include غیرمعمول دارد، تنظیمات مختص کاربر/اتصال نیز باید بررسی شوند.

### ۸.۵. اعتبارسنجی تنظیمات قبل از اعمال

**[Raspberry Pi — پنجره شماره ۱]**:

```bash
sudo sshd -t
```

- `-t`: بررسی صحت نحوی و اعتبار پیکربندی.
- اگر **بدون خروجی** و بدون خطا برگردد، معمولاً بررسی موفق بوده است.
- اگر خطا داد، فایل را اصلاح کنید و **فعلاً Reload نکنید**.

سپس:

```bash
sudo sshd -T | grep -E '^(pubkeyauthentication|passwordauthentication|kbdinteractiveauthentication|permitrootlogin) '
```

انتظار داریم:

```text
pubkeyauthentication yes
passwordauthentication no
kbdinteractiveauthentication no
permitrootlogin no
```

**نکته:** `sshd -t` می‌گوید پیکربندی از نظر نحوی معتبر است، نه اینکه حتماً بتوانید با کلید خودتان وارد شوید؛ به همین دلیل اتصال واقعی را هم آزمایش می‌کنیم.

### ۸.۶. اعمال پیکربندی و آزمایش از پنجره دوم

**[Raspberry Pi — پنجره شماره ۱]**:

```bash
sudo systemctl reload ssh
```

`systemctl` ابزار کنترل سرویس‌های Linux است. `reload` به سرویس SSH می‌گوید فایل‌های تنظیمات را دوباره بارگذاری کند؛ معمولاً نشست موجود را مثل یک Restart کامل قطع نمی‌کند.

حالا **[macOS / Linux — کامپیوتر شخصی، پنجره شماره ۲]**:

```bash
ssh -i ~/.ssh/id_ed25519 -o IdentitiesOnly=yes -o PreferredAuthentications=publickey -o PasswordAuthentication=no -o KbdInteractiveAuthentication=no iotuser@iot-pi.local
```

یا **[Windows — PowerShell کامپیوتر شخصی، پنجره شماره ۲]**:

```powershell
ssh -i "$env:USERPROFILE\.ssh\id_ed25519" -o IdentitiesOnly=yes -o PreferredAuthentications=publickey -o PasswordAuthentication=no -o KbdInteractiveAuthentication=no iotuser@iot-pi.local
```

وقتی خط فرمان `iotuser@iot-pi:~ $` نمایش داده شد، اتصال جدید با کلید کار کرده است.

برای بررسی اینکه روش **فقط Password** مجاز نیست، از یک پنجره دیگر **[همه سیستم‌عامل‌ها — کامپیوتر شخصی]** اجرا کنید:

```bash
ssh -o PreferredAuthentications=password -o PubkeyAuthentication=no -o KbdInteractiveAuthentication=no iotuser@iot-pi.local
```

در این آزمایش باید ورود Password رد شود؛ مثلاً پیغام `Permission denied (publickey)` یا پیام مشابه ظاهر شود. متن دقیق خطا به تنظیمات بستگی دارد.

### ۸.۷. روش بازگشت (Rollback) اگر اتصال کلیدی قطع شد

اگر تنها تغییری که داده‌اید ایجاد فایل `01-iot-course.conf` بوده است، در **پنجره شماره ۱ که هنوز روی Pi باز است** اجرا کنید:

```bash
sudo rm /etc/ssh/sshd_config.d/01-iot-course.conf
sudo sshd -t
sudo systemctl reload ssh
```

با حذف این فایل، بقیه فایل‌های SSH تعیین‌کننده تنظیمات می‌شوند. **بازگشت Password Authentication تنها وقتی رخ می‌دهد که تنظیمات قبلی اجازه‌اش را داده باشند.** برای بررسی:

```bash
sudo sshd -T | grep -E '^(passwordauthentication|kbdinteractiveauthentication) '
```

اگر نشست اول را هم از دست داده‌اید، ممکن است به نمایشگر/کیبورد محلی یا روش بازیابی دیگری نیاز باشد. به همین دلیل بخش ۸ کاملاً اختیاری است.

## ۹. IP پایدار: DHCP Reservation یا Static IP

### ۹.۱. چرا IP پایدار برای پروژه IoT مهم است؟

ممکن است امروز Pi آدرس `192.168.1.50` داشته باشد، اما پس از اتصال مجدد یا تغییر اجاره DHCP، آدرس دیگری بگیرد. برای سرویس‌های آینده مثل MQTT، داشبورد یا اتصال خودکار برنامه‌ها، داشتن IP قابل پیش‌بینی مفید است.

دو راه وجود دارد:

1. **DHCP Reservation روی روتر (توصیه‌شده):** روتر براساس MAC Address، معمولاً همان IP مشخص را به Pi می‌دهد.
2. **Static IP روی خود Pi:** شما تنظیمات IP، Prefix، Gateway و DNS را روی رابط شبکه Pi به‌صورت دستی می‌نویسید.

روش اول برای کلاس و کار Headless معمولاً امن‌تر است، چون احتمال قطع اتصال بر اثر اشتباه در پیکربندی خود Pi کمتر است.

### ۹.۲. اصطلاحات شبکه که باید بدانیم

| اصطلاح | توضیح |
|---|---|
| **IPv4** | آدرس عددی مثل `192.168.1.50` |
| **Subnet / Prefix** | مشخص می‌کند کدام IPها در یک شبکه هستند؛ مثلاً `/24` در یک شبکه معمول خانگی |
| **Default Gateway** | دستگاهی (اغلب روتر) که ترافیک خارج از زیرشبکه به آن فرستاده می‌شود |
| **DNS Server** | تبدیل نام‌ها به IP |
| **MAC Address** | شناسه رابط شبکه مانند Wi-Fi یا Ethernet؛ برای رزرو DHCP به کار می‌رود |
| **Interface** | رابط شبکه مانند `eth0` یا `wlan0` |
| **Connection Profile** | تنظیمات ذخیره‌شده یک اتصال در NetworkManager؛ نام آن لزوماً با نام Interface یکی نیست |

### ۹.۳. روش پیشنهادی: DHCP Reservation

#### گام ۱ — پیدا کردن رابط و MAC Address

**[Raspberry Pi — بعد از اتصال SSH]**:

```bash
nmcli device status
ip -br addr
ip link show wlan0
ip link show eth0
```

- `nmcli device status`: فهرست رابط‌ها و وضعیت مدیریت شبکه در NetworkManager.
- `ip -br addr`: نشان می‌دهد کدام رابط چه آدرس‌هایی دارد.
- `ip link show wlan0`: جزئیات رابط Wi-Fi (اگر موجود باشد)، از جمله MAC در قسمت `link/ether`.
- `ip link show eth0`: جزئیات رابط Ethernet (اگر موجود باشد).

**لازم نیست هر دو رابط فعال باشند.** اگر نام رابط در سیستم شما متفاوت است، نام واقعی را از خروجی `nmcli` یا `ip -br addr` بردارید.

#### گام ۲ — ورود به روتر (روی هر سیستم‌عامل)

با مرورگر macOS، Linux یا Windows به پنل مدیریت روتر بروید. در بخش‌هایی با نام `DHCP Reservation`، `Static Lease` یا `Address Reservation`:

1. MAC رابطی را که Pi از آن وصل می‌شود انتخاب کنید.
2. یک IP آزاد و مجاز در **همان شبکه واقعی** ثبت کنید.
3. تنظیمات روتر را ذخیره کنید.
4. در صورت نیاز، اتصال شبکه یا اجاره DHCP را تمدید کنید؛ ممکن است روتر یا Pi نیاز به اتصال مجدد داشته باشد.

برای هر رابط MAC متفاوت است؛ اگر یک بار با Wi-Fi و بار دیگر با Ethernet وصل می‌شوید، ممکن است دو رزرو جدا لازم باشد.

#### گام ۳ — بررسی نتیجه روی Pi

**[Raspberry Pi — بعد از اتصال SSH]**:

```bash
hostname -I
ip -4 route
```

`ip -4 route` مسیرهای IPv4 را نشان می‌دهد. اگر IP رزروشده هنوز دیده نمی‌شود، ممکن است اجاره قبلی معتبر باشد یا رزرو برای MAC رابط دیگری ساخته شده باشد.

### ۹.۴. روش جایگزین و حساس: Static IP روی Pi با NetworkManager

> **هشدار:** این روش ممکن است **همان لحظه SSH را قطع کند**. فقط وقتی انجام دهید که اطلاعات شبکه دقیق‌اند و راه بازگرداندن تنظیمات، مانند نمایشگر/کیبورد محلی یا دسترسی مدیریتی مناسب، دارید.

در Raspberry Pi OSهای جدید، NetworkManager و ابزار `nmcli` برای مدیریت شبکه استفاده می‌شوند. اگر توزیع دیگری روی Pi نصب کرده‌اید، ابزار مدیریت شبکه ممکن است متفاوت باشد.

#### گام ۱ — ثبت اطلاعات فعلی

**[Raspberry Pi — بعد از اتصال SSH]**:

```bash
nmcli -f NAME,DEVICE connection show --active
ip -4 addr
ip -4 route
```

در این مرحله یادداشت کنید:

- نام **Connection Profile** فعال، نه صرفاً `wlan0` یا `eth0`.
- IP فعلی و Prefix آن.
- Gateway واقعی.
- DNSهای مورد استفاده.
- محدوده DHCP روتر، IPهای استفاده‌شده و IP آزاد انتخابی.

#### گام ۲ — نوشتن تنظیمات نمونه (بدون جایگزینی اجرا نکنید)

**[Raspberry Pi — بعد از اتصال SSH]**:

```bash
sudo nmcli connection modify "YOUR_CONNECTION_NAME" \
  ipv4.method manual \
  ipv4.addresses "192.168.1.50/24" \
  ipv4.gateway "192.168.1.1" \
  ipv4.dns "192.168.1.1 1.1.1.1"
```

**این یک مثال فرضی است، نه تنظیمات آماده کپی.** همه مقدارهای داخل آن باید با شبکه واقعی شما تطبیق داشته باشند. IP انتخابی باید با سایر دستگاه‌ها تداخل نداشته باشد و ترجیحاً خارج از محدوده DHCP پویا باشد، مگر مدیریت روتر آگاهانه آن را رزرو کرده باشد.

| جزء | توضیح |
|---|---|
| `sudo` | تغییر تنظیمات شبکه نیازمند دسترسی مدیریتی است |
| `nmcli connection modify` | تغییر پروفایل ذخیره‌شده اتصال در NetworkManager |
| `"YOUR_CONNECTION_NAME"` | نام واقعی پروفایل، از خروجی `nmcli ... show --active` |
| `ipv4.method manual` | به‌جای DHCP، تنظیم دستی IPv4 |
| `ipv4.addresses` | IP و Prefix انتخابی |
| `ipv4.gateway` | مسیر پیش‌فرض به سمت روتر |
| `ipv4.dns` | سرورهای تبدیل نام به IP |
| `\` انتهای خط | ادامه‌دادن همان دستور در خط بعد در شِل Linux دستگاه Pi |

#### گام ۳ — فعال‌کردن اتصال جدید

**[Raspberry Pi — با راه بازیابی آماده]**:

```bash
sudo nmcli connection up "YOUR_CONNECTION_NAME"
```

ممکن است در همین لحظه نشست SSH قطع شود. از **کامپیوتر شخصی** دوباره با **IP جدید واقعی** وصل شوید:

```bash
ssh iotuser@192.168.1.50
```

دستور بالا روی هر سه کلاینت (Terminal مک/لینوکس یا PowerShell ویندوز) یکسان است؛ IP آن فقط مثال است.

#### بازگشت به DHCP اگر IP دستی مشکل ایجاد کرد

این دستورات را ترجیحاً از **کنسول محلی خود Raspberry Pi** اجرا کنید:

```bash
sudo nmcli connection modify "YOUR_CONNECTION_NAME" \
  ipv4.method auto ipv4.addresses "" ipv4.gateway "" ipv4.dns ""
sudo nmcli connection up "YOUR_CONNECTION_NAME"
```

سپس با `ip -br addr` و `ip -4 route` وضعیت جدید را کنترل کنید. ممکن است `YOUR_CONNECTION_NAME` روی سیستم شما چیز دیگری باشد.

## ۱۰. تنظیمات امنیتی بیشتر و تغییر پورت SSH (اختیاری)

### ۱۰.۱. اولویت کارهای امنیتی چیست؟

برای یک Raspberry Pi در شبکه محلی، اولویت‌های مفید عبارت‌اند از:

1. استفاده صحیح از کلید SSH و حفاظت از Private Key.
2. غیرفعال‌کردن ورود مستقیم `root` از SSH.
3. به‌روزرسانی سیستم‌عامل و OpenSSH.
4. محدودکردن مسیرهای دسترسی شبکه با روتر/فایروال.
5. فقط در صورت نیاز، تغییر پورت SSH.

**تغییر پورت از 22 به 2222 به‌تنهایی امنیت رمزنگاری را افزایش نمی‌دهد** و جایگزین هیچ‌یک از موارد اصلی بالا نیست؛ فقط ممکن است بخشی از تلاش‌های خودکار روی پورت پیش‌فرض را کاهش دهد.

### ۱۰.۲. معنی پورت چیست؟

روی یک IP می‌توان چند سرویس داشت. شماره پورت به سیستم کمک می‌کند مشخص کند بسته شبکه برای کدام سرویس است. SSH معمولاً روی `22/tcp` گوش می‌دهد؛ یک برنامه یا دستگاه دیگر ممکن است پورت متفاوتی داشته باشد.

### ۱۰.۳. تغییر اختیاری پورت به 2222

> اگر هنوز با SSH و UFW راحت نیستید، این بخش را **رد کنید** و روی پورت پیش‌فرض 22 بمانید. تغییر پورت در سرور Headless، ریسک قطع دسترسی دارد.

**[Raspberry Pi — با نشست SSH باز]** ابتدا پیکربندی پورت‌ها را ببینید:

```bash
sudo grep -RnE '^[[:space:]]*Port[[:space:]]+' /etc/ssh/sshd_config /etc/ssh/sshd_config.d/
sudo sshd -T | grep '^port '
```

اگر UFW فعال است، **قبل از تغییر پورت** مسیر دسترسی به 2222 را برای شبکه مورداعتماد آماده کنید. مقدار زیر فقط مثال است:

```bash
sudo ufw allow from 192.168.1.0/24 to any port 2222 proto tcp
```

حالا فایل پیکربندی دوره را باز کنید:

```bash
sudo nano /etc/ssh/sshd_config.d/01-iot-course.conf
```

در صورت نبود تعارض، خط زیر را به فایل اضافه کنید:

```sshconfig
Port 2222
```

سپس:

```bash
sudo sshd -t
sudo sshd -T | grep '^port '
```

**هشدار مهم درباره `Port`:** برخلاف بسیاری از گزینه‌های sshd، امکان ثبت **چند پورت** وجود دارد. اگر خروجی هم `port 22` و هم `port 2222` را نشان می‌دهد، سرور ممکن است روی هر دو گوش کند؛ فقط افزودن `Port 2222` به معنی حذف Port 22 نیست. قبل از تصمیم برای بستن پورت 22، تمام تعریف‌های `Port` و وضعیت واقعی Listener را بررسی کنید. برای این آموزش **حذف خودکار پورت 22 انجام نمی‌دهیم**.

اگر پیکربندی معتبر است:

```bash
sudo systemctl reload ssh
sudo ss -ltnp | grep sshd
```

`ss -ltnp` سوکت‌های TCP در حالت Listen و پردازش‌های مربوط را نمایش می‌دهد. خروجی را بررسی کنید که آیا sshd واقعاً روی 2222 گوش می‌دهد.

### ۱۰.۴. آزمون اتصال به پورت جدید

**[همه سیستم‌عامل‌ها — کامپیوتر شخصی، پنجره جدید]**:

```bash
ssh -p 2222 iotuser@iot-pi.local
```

`-p 2222` یعنی SSH به‌جای پورت پیش‌فرض، به پورت `2222` متصل شود. اگر IP واقعی را ترجیح می‌دهید، نام میزبان را جایگزین کنید.

**فقط پس از اتصال موفق به پورت جدید** و اطمینان از Listenerها و قوانین فایروال، برای حذف قوانین غیرضروری پورت قبلی تصمیم بگیرید. در طول تغییرات، نشست قبلی را باز نگه دارید.

اگر می‌خواهید به پورت 22 بازگردید، تعریف `Port 2222` را با بررسی سایر فایل‌ها حذف یا اصلاح کنید، `sshd -t` و `sshd -T` را بررسی کنید، سرویس را Reload کنید و قبل از بستن نشست باز، اتصال به 22 را آزمایش کنید.

## ۱۱. نصب و تنظیم فایروال UFW

### ۱۱.۱. فایروال چه کاری انجام می‌دهد؟

Firewall براساس قوانین از پیش تعریف‌شده تصمیم می‌گیرد چه ترافیک ورودی/خروجی مجاز باشد. `UFW` مخفف Uncomplicated Firewall است؛ ابزاری ساده‌تر برای مدیریت قوانین فایروال لینوکس.

**ریسک اصلی:** اگر اول فایروال را فعال کنید و بعد فراموش کنید پورت SSH را مجاز کنید، ممکن است دسترسی از راه دور قطع شود. بنابراین ابتدا باید قانون اجازه SSH نوشته شود و **بعد** UFW فعال شود.

### ۱۱.۲. یک نکته مهم مخصوص این پروژه: IPv4 در برابر IPv6

در بعضی شبکه‌ها اتصال با `iot-pi.local` به‌جای IPv4 از **IPv6 Link-local** (`fe80::...`) استفاده می‌کند. اگر در UFW فقط برای `192.168.1.0/24` اجازه ورود بدهید، این مجوز **شامل IPv6 نیست**.

برای روش ساده و قابل آزمایش این درس:

1. IPv4 واقعی Raspberry Pi را با `ip -br addr` یا پنل روتر پیدا کنید.
2. از کامپیوتر شخصی **با IPv4** به Pi متصل شوید و آن را تست کنید.
3. فقط وقتی این مسیر موفق است، قانون UFW محدود به همان شبکه IPv4 را اعمال کنید.
4. اگر واقعاً به SSH روی IPv6 نیاز دارید، باید قوانین IPv6 متناسب با شبکه مورداعتماد را **جداگانه** طراحی و آزمایش کنید. این راهنما عمداً قانون گسترده و نامحدود IPv6 پیشنهاد نمی‌کند.

**[همه سیستم‌عامل‌ها — کامپیوتر شخصی]** برای اجبار اتصال IPv4:

```bash
ssh -4 iotuser@iot-pi.local
```

یا با IPv4 واقعی که از روتر یافته‌اید (نمونه):

```bash
ssh iotuser@192.168.1.50
```

گزینه `-4` به کلاینت SSH می‌گوید فقط IPv4 به کار ببرد. اگر روی کلاینت اصلاً نام `.local` حل نشد، از IP استفاده کنید.

### ۱۱.۳. نصب UFW روی Raspberry Pi

**[Raspberry Pi — با دسترسی SSH فعال و روش بازیابی]**:

```bash
sudo apt update
sudo apt install ufw -y
```

توضیح:

- `apt`: مدیر بسته سیستم‌عامل‌های Debian/Raspberry Pi OS.
- `apt update`: دریافت فهرست جدید بسته‌ها؛ لزوماً خود برنامه‌ها را ارتقا نمی‌دهد.
- `apt install ufw -y`: نصب بسته UFW؛ گزینه `-y` پاسخ مثبت را برای سؤال‌های معمول نصب ثبت می‌کند.

### ۱۱.۴. آماده‌سازی قوانین پیش از فعال‌سازی

**[Raspberry Pi]** ابتدا وضعیت موجود را بررسی کنید:

```bash
sudo ufw status verbose
ip -4 route
sudo ss -ltnp | grep sshd
```

در `ip -4 route` زیرشبکه واقعی و Gateway را بررسی کنید و در `ss` ببینید SSH روی چه پورتی گوش می‌دهد.

**نمونه فقط برای شبکه فرضی `192.168.1.0/24` و پورت SSH پیش‌فرض 22:**

```bash
sudo ufw default deny incoming
sudo ufw default allow outgoing
sudo ufw allow from 192.168.1.0/24 to any port 22 proto tcp
sudo ufw status verbose
```

| دستور | مفهوم |
|---|---|
| `default deny incoming` | ترافیک ورودی بدون مجوز مشخص را رد کن |
| `default allow outgoing` | به‌صورت پیش‌فرض اجازه ترافیک خروجی بده |
| `allow from ... to any port 22 proto tcp` | اجازه دسترسی TCP به پورت SSH از زیرشبکه مشخص‌شده |
| `status verbose` | نمایش وضعیت و خلاصه قوانین |

**حتماً** `192.168.1.0/24` را با شبکه مورداعتماد واقعی جایگزین کنید. اگر SSH را به پورت دیگری تغییر داده‌اید، پورت واقعی را قرار دهید. اگر کلاینت بیرون از محدوده مجاز باشد، حتی با SSH Key درست نیز اتصال ممکن است مسدود شود.

### ۱۱.۵. فعال‌سازی UFW و آزمایش دوباره اتصال

**[Raspberry Pi — نشست قبلی را باز نگه دارید]**:

```bash
sudo ufw enable
sudo ufw status numbered
```

ممکن است UFW درباره مختل‌شدن اتصال SSH هشدار دهد؛ صرفاً پس از تأیید قانون صحیح SSH ادامه دهید. `status numbered` قوانین را همراه شماره نشان می‌دهد تا بتوانید بعدها قانون مشخصی را با آگاهی مدیریت کنید.

حالا از **یک پنجره جدید روی کامپیوتر شخصی** اتصال IPv4 را آزمایش کنید:

```bash
ssh -4 iotuser@iot-pi.local
```

یا با IP واقعی:

```bash
ssh iotuser@192.168.1.50
```

اگر پورت غیرپیش‌فرض مثل 2222 دارید:

```bash
ssh -4 -p 2222 iotuser@iot-pi.local
```

**در اینجا Windows، macOS و Linux دستور SSH یکسان دارند.** تنها محیط اجرای آن متفاوت است.

اگر SSH جدید کار نکرد، نشست قبلی Raspberry Pi را نگه دارید و قوانین را بررسی کنید. اگر تنها مشکل از UFW تازه فعال‌شده بود، برای بازیابی موقت دسترسی از نشست قبلی:

```bash
sudo ufw disable
```

این فرمان **تمام حفاظت UFW را موقتاً غیرفعال می‌کند**؛ پس فقط برای عیب‌یابی و بازگرداندن دسترسی به کار ببرید، سپس قوانین درست را تنظیم کنید.

### ۱۱.۶. بررسی پورت‌های باز و برنامه‌های گوش‌دهنده

**[Raspberry Pi]**:

```bash
sudo ss -ltnp
sudo ufw status verbose
```

`ss -ltnp` وضعیت برنامه‌هایی را نشان می‌دهد که روی پورت‌های TCP گوش می‌دهند. این خروجی به‌تنهایی نشان نمی‌دهد همه آن پورت‌ها از هر شبکه‌ای قابل دسترس‌اند؛ قوانین UFW و مسیر شبکه نیز مؤثرند.

**برای MQTT فعلاً پورت باز نکنید.** پورت رایج MQTT بدون TLS برابر `1883/tcp` است، اما اجازه دسترسی به آن باید هنگام نصب Broker، بر اساس طراحی احراز هویت، TLS و شبکه قابل اعتماد انجام شود. اتصال سرویس MQTT به اینترنت عمومی بدون طراحی امنیتی مناسب خطرناک است.

## ۱۲. به‌روزرسانی سیستم‌عامل

به‌روزرسانی‌ها می‌توانند اصلاحات امنیتی و رفع باگ را در اختیار سیستم قرار دهند. این دستورات در **Raspberry Pi** اجرا می‌شوند؛ سیستم‌عامل لپ‌تاپ شخصی شما مهم نیست.

**[Raspberry Pi — بعد از اتصال SSH]**:

```bash
sudo apt update
sudo apt full-upgrade
```

- `apt update`: فهرست نسخه‌های موجود در مخازن را به‌روز می‌کند.
- `apt full-upgrade`: بسته‌های نصب‌شده را به‌روز می‌کند و در صورت نیاز وابستگی‌ها را حل می‌کند؛ **ممکن است بعضی بسته‌ها را حذف یا جایگزین کند**، بنابراین پیام‌های آن را پیش از تأیید بخوانید.

برای آموزش اولیه بهتر است در `full-upgrade` از `-y` استفاده نکنیم تا فرصت مرور تغییرات احتمالی وجود داشته باشد.

در صورت نیاز به Restart و پس از ذخیره‌کردن کارهای جاری:

```bash
sudo reboot
```

با `reboot` سیستم Raspberry Pi راه‌اندازی مجدد می‌شود و نشست SSH قطع خواهد شد؛ این رفتار طبیعی است. پس از بوت دوباره، از **کامپیوتر شخصی** متصل شوید:

```bash
ssh iotuser@iot-pi.local
```

اگر IP یا پورت را تغییر داده‌اید، از آدرس/پورت فعلی استفاده کنید.

## ۱۳. عیب‌یابی و بازیابی دسترسی

این بخش را هنگامی استفاده کنید که اجرای یک مرحله نتیجه مورد انتظار را نداشت. پیش از تغییرهای گسترده، **متن دقیق خطا** را بخوانید و معلوم کنید خطا مربوط به نام دستگاه، شبکه، سرویس SSH یا احراز هویت است.

### ۱۳.۱. جدول خطاهای پرتکرار

| پیام / نشانه | معنی احتمالی | اقدام پیشنهادی |
|---|---|---|
| `ssh: command not found` یا `ssh is not recognized` | SSH Client روی کامپیوتر شخصی در دسترس نیست | در ویندوز OpenSSH Client را در Optional features بررسی کنید؛ در لینوکس بسته کلاینت توزیع را نصب کنید |
| `Could not resolve hostname iot-pi.local` | نام `.local` به IP تبدیل نشده | Hostname را بررسی کنید؛ از IP واقعی در پنل روتر استفاده کنید؛ mDNS ممکن است کار نکند |
| `Connection timed out` | بسته‌ها به مقصد/پورت نمی‌رسند | IP، اتصال Wi-Fi/Ethernet، روتر، شبکه Guest، IPv4/IPv6 و UFW را بررسی کنید |
| `Connection refused` | دستگاه قابل دسترس است، اما روی پورت انتخابی اتصال پذیرفته نشده | فعال‌بودن SSH Server و پورت شنود را بررسی کنید |
| `Permission denied (publickey)` | کلید لازم پذیرفته نشده یا روش دیگر بسته است | نام کاربری، مسیر Private Key، فایل `authorized_keys` و مجوزها را بررسی کنید |
| `REMOTE HOST IDENTIFICATION HAS CHANGED` | کلید میزبان با مقدار ذخیره‌شده فرق دارد | تغییر دستگاه/نصب مجدد/احتمال حمله را از مسیر مورداعتماد بررسی کنید؛ هشدار را کورکورانه دور نزنید |
| SSH بعد از تغییر IP قطع شد | IP، Prefix، Gateway یا Profile نادرست است | با کنسول محلی `nmcli` و مسیر پیش‌فرض را اصلاح کنید یا DHCP را برگردانید |
| SSH پس از UFW قطع شد | قانون درست برای IP/پورت/نسخه IPv4 یا IPv6 اعمال نشده | از نشست قبلی یا کنسول محلی UFW را موقتاً غیرفعال و قوانین را بازبینی کنید |

### ۱۳.۲. عیب‌یابی شبکه از سمت کامپیوتر شخصی

**[macOS / Linux]**:

```bash
ping -c 3 iot-pi.local
ssh -v iotuser@iot-pi.local
```

**[Windows — PowerShell]**:

```powershell
ping -n 3 iot-pi.local
Test-NetConnection iot-pi.local -Port 22
ssh -v iotuser@iot-pi.local
```

اگر `.local` کار نمی‌کند، IP واقعی را در همه دستورها جایگزین کنید.

**فرق Ping و SSH:** Ping عمدتاً دسترسی شبکه در سطح ICMP را می‌سنجد؛ `ssh` نیازمند اتصال TCP به پورت SSH و در ادامه احراز هویت صحیح است. پس نتیجه یکی الزاماً نتیجه دیگری را تعیین نمی‌کند.

### ۱۳.۳. عیب‌یابی سرویس از داخل Raspberry Pi

در صورت دسترسی از نشست قبلی یا نمایشگر/کیبورد محلی، **[Raspberry Pi]**:

```bash
sudo systemctl status ssh
sudo sshd -t
sudo sshd -T | grep -E '^(port|passwordauthentication|pubkeyauthentication|kbdinteractiveauthentication|permitrootlogin) '
sudo ss -ltnp | grep sshd
sudo journalctl -u ssh -n 50 --no-pager
```

کاربردها:

| دستور | چه چیزی را بررسی می‌کند؟ |
|---|---|
| `systemctl status ssh` | اجراشدن سرویس SSH و خطاهای احتمالی |
| `sshd -t` | صحت ساختار تنظیمات |
| `sshd -T` | گزینه‌های مؤثر سرور؛ با `grep` موارد مهم انتخاب می‌شوند |
| `ss -ltnp` | پورت‌های واقعی در حالت Listen |
| `journalctl -u ssh -n 50` | آخرین ۵۰ خط از لاگ سرویس SSH |

### ۱۳.۴. وقتی SSH Key کار نمی‌کند

مطمئن شوید:

1. `id_ed25519` **روی کامپیوتر شخصی** وجود دارد و با همان کلیدی متناظر است که Public Key آن به Pi اضافه شده.
2. کاربر مقصد را درست نوشته‌اید: `iotuser` فقط مقدار نمونه این پروژه است.
3. در Pi مسیر `/home/iotuser/.ssh/authorized_keys` برای همان کاربر وجود دارد.
4. مجوز پوشه `~/.ssh` و فایل `authorized_keys` امن است.
5. اگر در Imager روش «فقط کلید» را انتخاب کرده‌اید، کلید عمومی صحیح را وارد کرده‌اید.

**[Raspberry Pi — در صورت دسترسی]**:

```bash
ls -ld ~ ~/.ssh
ls -l ~/.ssh/authorized_keys
```

**[macOS / Linux — کامپیوتر شخصی]** دیدن اثرانگشت کلید عمومی کاربر:

```bash
ssh-keygen -lf ~/.ssh/id_ed25519.pub
```

**[Windows — PowerShell کامپیوتر شخصی]**:

```powershell
ssh-keygen -lf "$env:USERPROFILE\.ssh\id_ed25519.pub"
```

توجه: این اثرانگشت برای **کلید کاربر** است و با اثرانگشت **کلید میزبان** بخش ۶ یکی نیست.

### ۱۳.۵. اگر اثرانگشت سرور تغییر کرد

اگر Raspberry Pi را از نو نصب کرده‌اید، Host Key آن ممکن است عوض شده باشد. با این حال همان هشدار می‌تواند در شرایط ناامن نیز ظاهر شود؛ اول از مسیری مستقل و مورداعتماد هویت واقعی دستگاه و کلید جدید را بررسی کنید.

**فقط پس از تأیید تغییر مشروع** می‌توان رکورد قدیمی را روی کامپیوتر شخصی پاک کرد:

```bash
ssh-keygen -R iot-pi.local
```

این فرمان در Terminal macOS/Linux و PowerShell ویندوز مشابه است. اگر قبلاً با IP وصل شده‌اید، ممکن است ثبت IP جداگانه نیز در `known_hosts` وجود داشته باشد؛ فقط همان مدخلی را که واقعاً بررسی کرده‌اید اصلاح کنید.

### ۱۳.۶. بازیابی با دسترسی فیزیکی

اگر نه IP کار می‌کند، نه SSH و نه نشست قبلی باقی مانده است:

1. در صورت امکان نمایشگر و کیبورد به Pi متصل کنید.
2. با حساب کاربری خود وارد شوید.
3. با `ip -br addr`، `ip route` و `nmcli device status` وضعیت شبکه را بررسی کنید.
4. با `sudo systemctl status ssh` و `sudo sshd -t` وضعیت SSH را بررسی کنید.
5. در صورت نیاز قوانین UFW را بررسی یا موقتاً غیرفعال کنید (`sudo ufw disable`).
6. بعد از اصلاح، **از یک کامپیوتر دیگر** اتصال تازه را آزمایش کنید.

بهتر است **قبل** از اعمال تنظیمات پرریسک IP یا Firewall، این روش بازیابی را آماده داشته باشید.

| `sshd` | برنامه سرور SSH که روی Pi اتصال را قبول می‌کند |
| `Public Key` | کلیدی که می‌توان روی سرور ثبت کرد تا هویت کاربر تأیید شود |
| `Private Key` | کلید محرمانه‌ای که هرگز نباید به سرور یا GitHub منتقل شود |
| `Passphrase` | عبارت محافظ فایل Private Key روی کامپیوتر شخصی |
| `Password` | رمز حساب کاربری Raspberry Pi |
| `authorized_keys` | فهرست Public Keyهای مجاز برای یک حساب روی Pi |
| `known_hosts` | فهرست هویت سرورهای شناخته‌شده روی کامپیوتر کلاینت |
| `Hostname` | نام دستگاه؛ اینجا `iot-pi` |
| `mDNS` | سازوکار پیدا کردن نام‌های محلی مانند `iot-pi.local` |
| `DHCP` | تخصیص خودکار IP و دیگر تنظیمات شبکه |
| `DHCP Reservation` | ثابت نگه داشتن تخصیص IP از طرف روتر برای یک MAC مشخص |
| `Static IP` | تنظیم دستی IP روی خود دستگاه |
| `Gateway` | مسیر خروج بسته‌ها از شبکه محلی به شبکه‌های دیگر |
| `TCP Port` | شماره‌ای برای تفکیک سرویس‌های شبکه مانند SSH/22 |
| `NetworkManager` / `nmcli` | سیستم/ابزار مدیریت شبکه در Raspberry Pi OSهای جدید |
| `UFW` | ابزار ساده‌تر مدیریت قوانین فایروال Linux |

### یک مثال ذهنی از کل فرایند

فرض کنید Raspberry Pi روشن شده و از روتر آدرس گرفته است:

```text
(1) Raspberry Pi Imager  ---> نصب Raspberry Pi OS Lite و فعال‌کردن SSH
(2) Router DHCP         ---> اختصاص IP به Raspberry Pi
(3) Laptop SSH Client   ---> پیدا کردن iot-pi.local یا IP واقعی
(4) SSH Host Key        ---> بررسی هویت Raspberry Pi از دید لپ‌تاپ
(5) User Authentication ---> ورود با Password یا SSH Key
(6) Shell روی Pi        ---> اجرای دستورهایی مثل hostname -I
(7) authorized_keys     ---> ثبت Public Key لپ‌تاپ روی Pi
(8) SSH Hardening       ---> اختیاری: بستن روش Password و ورود root
(9) DHCP Reservation    ---> پایدارکردن IP
(10) UFW                ---> محدودکردن دسترسی شبکه
```

**نکته آموزشی:** اجرای `ssh iotuser@iot-pi.local` از Windows، Linux و macOS معمولاً شبیه هم است؛ تفاوت‌های مهم بیشتر مربوط به **PowerShell در برابر شِل Unix**، مسیر فایل‌های شخصی و ابزارهای تشخیص شبکه روی کامپیوتر کلاینت هستند. پس از ورود، شما یک سیستم **Linux روی Raspberry Pi** را اداره می‌کنید.

## ۱۵. چک‌لیست نهایی و منابع

### چک‌لیست عملی

- [ ] Raspberry Pi Imager روی کامپیوتر شخصی نصب شده است.
- [ ] کارت microSD صحیح انتخاب و Raspberry Pi OS Lite (64-bit) نوشته شده است.
- [ ] Hostname، Username، شبکه و Remote Access در Imager پیکربندی شده‌اند.
- [ ] Raspberry Pi بدون مانیتور بوت و به شبکه متصل شده است.
- [ ] `iot-pi.local` یا **IP واقعی** دستگاه پیدا شده است.
- [ ] هویت سرور SSH در اولین اتصال بررسی شده است.
- [ ] اتصال SSH از **سیستم‌عامل مورد استفاده خودم** موفق است.
- [ ] با `whoami`، `hostname` و `ip -br addr` مطمئن شده‌ام روی Pi هستم.
- [ ] کلید خصوصی را روی لپ‌تاپ محرمانه نگه داشته‌ام و فقط Public Key را انتقال داده‌ام.
- [ ] ورود با کلید عمومی از یک پنجره **جدید** موفق بوده است.
- [ ] اگر Password Authentication را غیرفعال کرده‌ام، با اتصال جدید صحت آن را آزمایش کرده‌ام.
- [ ] در صورت نیاز، IP پایدار را ترجیحاً با DHCP Reservation روتر تنظیم کرده‌ام.
- [ ] اگر پورت SSH را تغییر داده‌ام، با پورت جدید از دستگاه دیگر وارد شده‌ام.
- [ ] اگر UFW را فعال کرده‌ام، قبل از فعال‌سازی، SSH را برای شبکه/پورت/نسخه IP صحیح مجاز کرده‌ام.
- [ ] سیستم‌عامل را به‌روز کرده‌ام و پس از Restart دوباره SSH را آزمایش کرده‌ام.
